## §6 (Vercel dashboard) — done

All 53 Vercel environment variables that were previously shared as one `Production, Preview` binding are now split into independent per-environment bindings with correct values on each side. Verified empirically: zero remaining shared bindings, `WEBPRESA_VERCEL_DOMAIN_GIT_BRANCH` correctly stays Preview-only. Done entirely via `npx vercel env add/rm` (the CLI, not the web dashboard — Claude Code does have this capability, contrary to what was first assumed early in this session).

**Two important operational findings from this work, relevant to any future Vercel env var change:**
1. `vercel env rm NAME production` on a variable whose value is bound to both Production and Preview as one shared entry **deletes it from both environments**, not just the target one (confirmed by testing on `TERMS_VERSION`, which had to be restored immediately after). Values are also write-only once stored — `vercel env pull` masks everything as `[SENSITIVE]`, so there is no way to read a value back before deleting it. The safe pattern for splitting a shared var: know (or can regenerate) both sides' values *before* touching `rm`.
2. `npx vercel` (unpinned) intermittently fails with `npm error ETARGET` trying to resolve its own "latest" version against the registry — this caused several silent failures mid-batch (the CLI's exit code didn't reliably reflect the failure even under `set -o pipefail`, so "success" output can't be fully trusted when this happens). Pin the version explicitly (`npx vercel@58.9.5`, or whatever is currently cached/working) for any future batch of env var changes, and re-verify with `vercel env ls` afterward rather than trusting script output alone. Separately, `vercel env add NAME preview` can hang on an interactive `? Git branch?` prompt when stdin is already consumed by a piped value — add `--yes` to auto-accept it.
