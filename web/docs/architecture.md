### Schemas (`domain/schemas/`)

Zod v3 runtime validation. Schemas import status arrays from models; models do not import Zod.

- `PreviewContentSchema` is the enforcement point for AI-generated content. All AI output must pass this schema before storage.

- ID fields validated against prefix regex (`^biz_`, `^preview_`, etc.).

### Factories (`domain/factories/`)

Create valid records and validate them via `Schema.parse()` before returning. Any invalid input throws a `ZodError` — no invalid records enter the system.

## S3 asset storage

**Implemented in Stage 9.** Single private, encrypted bucket per environment — `webpresa-{env}-assets` — provisioned via the reusable `WebpresaBucket` construct (`infra/lib/constructs/webpresa-bucket.ts`), mirroring the `WebpresaTable` pattern. Wired into the existing `WebpresaDataStack` alongside the four tables (`infra/lib/stacks/data-stack.ts`) rather than a separate stack.

### `webpresa-dev-assets`

| | |
|---|---|
| Encryption | S3-managed (SSE-S3) |
| Public access | fully blocked (`BLOCK_ALL`) |
| SSL | enforced via bucket policy |
| Versioning | disabled (dev) / **enabled** (prod) |
| Removal policy | DESTROY (dev) / RETAIN (prod) |
| Lifecycle | abort incomplete multipart uploads after 7 days; expire objects tagged `retain=false` after 90 days |

### Key structure (single bucket, prefix-scoped)

```
scans/{businessId}/{scanId}/crawl.json
scans/{businessId}/{scanId}/extracted.json
scans/{businessId}/{scanId}/images/{imageId}.{ext}
scans/{businessId}/{scanId}/existing/desktop.png
scans/{businessId}/{scanId}/existing/mobile.png
scans/{businessId}/{scanId}/preview/desktop.png
scans/{businessId}/{scanId}/preview/mobile.png
previews/{businessId}/{previewId}/...
postcards/{businessId}/{postcardId}/...
businesses/{businessId}/assets/logo.{ext}
businesses/{businessId}/assets/photos/{n}.{ext}
```

`crawl.json` (Stage 13) is the sanitized raw Firecrawl response (markdown/links/images/structured-extraction JSON/metadata — `html`/`rawHtml` are never requested, so there's nothing to strip there; no secrets are ever present in a Firecrawl response). `extracted.json` (Stage 13) is the validated `WebsiteEnrichmentSnapshot`. `images/{imageId}.{ext}` (Stage 13) holds accepted/review-required website images discovered by Firecrawl, fetched and rehosted server-side — see "Firecrawl Website Enrichment" below. `existing/`/`preview/{desktop,mobile}.png` (Stage 14) are Playwright screenshot captures, each `ScanEvent` populating only the one subfolder matching its own `targetType` — see "Playwright Screenshots (Stage 14)" below. These are never proxied publicly (private only, signed-URL admin viewing).

Two prefixes have a public-facing read path, both through `app/api/assets/[...key]/route.ts` (the app's first Route Handler) — no other prefix is ever proxied, and the raw bucket itself stays fully private:
- `businesses/{businessId}/assets/...` (added in the Stage 11 foundation work) — admin-uploaded logo/photos, unconditionally.
- `scans/{businessId}/{scanId}/images/...` (added in Stage 13) — accepted/review-required scan-derived images only. The sibling `crawl.json`/`extracted.json` artifacts in the same scan folder are deliberately **not** matched by the route's `SCAN_IMAGE_KEY_PATTERN` regex and stay private, admin-viewable only via a short-lived `getSignedAssetUrl`.

Both paths stream via `getAsset()` with a one-year `Cache-Control`.

The `retain=false` object tag is *not yet written by anything* — Stage 9 only provisions the lifecycle rule. Stage 13 does not set it either (scan artifacts are kept indefinitely, matching `SitePreview`'s own "never delete history" convention); Stage 14 doesn't set it either, for the same reason (each capture is its own permanent `scanId` history entry). Stage 22 (postcards) remains an expected future adopter.

### Application-side access

- `web/lib/s3/client.ts` — `server-only` singleton `S3Client`, same region/credential pattern as `web/lib/db/client.ts` (`AWS_REGION`, `AWS_PROFILE` locally, `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` on Vercel). `getAssetsBucketName()` reads `ASSETS_BUCKET_NAME`.
- `web/lib/s3/assets.ts` — `server-only` generic helpers: `putAsset`, `getAsset` (returns `null` on `NoSuchKey`), `getSignedAssetUrl` (short-lived signed URL, 300s default, for private admin viewing). All three reject keys outside the `scans/`, `previews/`, `postcards/`, `businesses/` prefixes before calling S3.
- `ScanEvent.storageKeys` remains unpopulated by every stage — Stage 13 only ever writes `rawArtifactKey`/`extractedArtifactKey`/`images[].s3Key`, and Stage 14 writes the more specific `captureResults.desktop`/`.mobile[].storageKey` instead (see "Playwright Screenshots (Stage 14)" below) — `storageKeys` stays reserved, unused, for a possible future adopter. Any `Postcard` creative-file field also remains unpopulated (Stage 22).

### IAM

The `webpresa-vercel-dev` IAM user's `webpresa-dev-vercel-data-access` **CDK-managed policy** (`infra/lib/stacks/vercel-access-stack.ts` — migrated 2026-07-24 from a hand-run inline policy, see `deployment.md`) grants `s3:GetObject`/`PutObject`/`DeleteObject`/`ListBucket` scoped to the assets bucket only. Stage 13 runs entirely inside existing Next.js Server Actions on Vercel — no dedicated Lambda or execution role was introduced, so it reuses this existing broad grant rather than a prefix-scoped one. Stage 14's screenshot-capture Lambda is the first execution role that *is* properly scoped further — `s3:PutObject` only, restricted to the `scans/*/*/existing/*` and `scans/*/*/preview/*` prefixes (see "Playwright Screenshots (Stage 14)" below) — the pattern this note previously described as aspirational for a not-yet-created role. Stage 22 (postcard service) remains an expected future adopter of the same narrower approach.

## Stock image CDN (Phase 1 curated hero-photo fallback)

**Deployed to dev (2026-07-27).** Unlike every image described above, stock photography is never sensitive and is deliberately reused across many businesses' generated previews, so it's served publicly through **CloudFront** rather than the private-bucket + `/api/assets/[...key]` proxy pattern — the first CDN in this project. `infra/lib/stacks/stock-images-stack.ts` (`WebpresaStockImagesStack`):

- A `WebpresaBucket` (`webpresa-{env}-stock-images`) — stays exactly as private as every other bucket (`BLOCK_ALL`, unchanged construct). Public reads happen only through CloudFront's Origin Access Control, which CDK wires up automatically (bucket policy included) via `origins.S3BucketOrigin.withOriginAccessControl(bucket)`.
- A CloudFront `Distribution` (`CachePolicy.CACHING_OPTIMIZED`) in front of it.
- The `stock-image-metadata` DynamoDB table (see "DynamoDB tables" above) — named distinctly from the bucket to avoid a colliding CloudFormation export.

**Key structure**: `hero/{desktop|mobile}/{industry}/{imageId}.{ext}` (a `kind: 'hero'` `StockImage` — every image is independently uploaded via `web/lib/s3/stock-images.ts`'s single `uploadStockImage()` helper; there is no pairing between a desktop and a mobile record) and `general/{industry|'uncategorized'}/{imageId}.{ext}` (a `kind: 'general'` standalone image, unused by any auto-pick tier today — reserved for the Phase 2 browsable library). Every upload gets a fresh, never-reused key — "replacing" a stock image is always a new upload + new `StockImage` record + archiving the old one, never an overwrite — so this feature never needs a `CreateInvalidation` call. Each object's `Cache-Control` is set to `public, max-age=31536000, immutable` at upload time.

**Application-side access**: `web/lib/s3/client.ts`'s `getStockImagesBucketName()`/`getStockImagesCdnDomain()` (env vars `STOCK_IMAGES_BUCKET_NAME`/`STOCK_IMAGES_CDN_DOMAIN`); `web/lib/s3/stock-images.ts`'s `putStockImageObject`/`deleteStockImageObject`/`stockImageCdnUrl` plus the two upload helpers. `web/lib/db/stock-images.ts` is the DynamoDB repository (env var `STOCK_IMAGES_TABLE_NAME`).

**IAM**: `webpresa-{env}-vercel-data-access`'s new `S3StockImages` statement grants `PutObject`/`DeleteObject`/`ListBucket` only — deliberately **no** `GetObject`, since reads happen publicly via CloudFront, never through the app's own IAM identity (unlike the assets bucket's `S3Assets` statement, which does need `GetObject` for the private-bucket proxy route).

**`next.config.ts`**: the CloudFront domain is added to `images.remotePatterns` — required even with `images.unoptimized: true`, since that flag only disables Next/Image's optimization pipeline, not its remote-hostname validation for absolute URLs.

See `build_log.md`, "Stock image repository — curated hero-photo fallback (Phase 1)", for the full record.

### IAM

The `webpresa-vercel-dev` IAM user's `webpresa-dev-vercel-data-access` **CDK-managed policy** (`infra/lib/stacks/vercel-access-stack.ts`) grants `secretsmanager:GetSecretValue` scoped to all 9 dev secret ARNs, including `webpresa-dev-claim-token`, `webpresa-dev-capture-token`, and `webpresa-dev-internal-api`. **Marketing stage (2026-08-21) is the first feature to outgrow this single policy** — adding its 7 tables' grants directly to `DataAccessPolicy` exceeded IAM's 6,144-byte per-policy size ceiling (`ServiceLimitExceeded`, hit on a real deploy attempt, cleanly auto-rolled back). The 10-managed-policies-per-user ceiling this stack's own doc comment already anticipated is what made this the easy fix rather than a harder one; the next feature needing new grants should default to adding a third policy here too, well before this one has any real chance of also filling up.

## Brand Theme System

**Implemented 2026-07-14.** Replaces free-form AI-generated hex colors with a curated set of 10 professionally designed theme presets. No code path — AI or otherwise — may invent, blend, or free-type a color; the only decision anyone (a person or the model) makes is *which preset name* to use.

- `web/domain/constants/themes.ts` — `THEME_NAMES` (the 10 approved preset identifiers) and `DEFAULT_THEME_NAME` (`'classicBlue'`). Single source of truth for which names are valid, imported by both schemas and models — mirrors the `industries.ts` / `brand-tone.ts` pattern.
- `web/lib/themes.ts` — `THEMES: Record<ThemeName, BrandTheme>`, the actual palettes. Every `BrandTheme` carries `primary`, `accent`, `background`, `surface`, `text`, `mutedText`, `border`, `success`, `warning`, `danger` (all validated hex in tests), plus `displayName` and `bestFor` (the industries each preset is designed for — shown in the admin theme picker and fed to the AI selection prompt). `resolveThemePalette(theme)` is the single render-time lookup: it resolves `PreviewTheme.themeName` directly, or — for previews saved before this system existed — falls back to the default preset's neutrals with the legacy `primaryColor`/`accentColor` substituted in.
- `PreviewTheme.themeName` (`domain/models/site-preview.ts`) replaces free-form `primaryColor`/`accentColor` as the source of a preview's brand colors. The legacy fields remain on the type and schema (`PreviewThemeSchema` requires one or the other via `.refine()`) purely for backward compatibility with previews generated before this system — no code path may set them on a new preview.
- `Business.theme` (`domain/models/business.ts`) — the resolved preset persisted on the business record, so every regeneration reuses it instead of re-deriving it. Editable via the "Theme" field on `BusinessDetailsForm.tsx` (an "Auto" option plus the 10 named presets); leaving it on Auto clears any stored override and lets selection run again on the next generation.

### Selection logic (`web/lib/theme/`)

- `logo-color.ts` — `detectLogoThemeFamily(logoUrl)` (Step 1: existing branding). Reads the logo from S3 via `getAsset()`, uses `sharp` to flatten transparency onto white and downsample to a single pixel (a cheap stand-in for a full dominant-color histogram), converts that average RGB to HSL, and classifies the hue/saturation/lightness into the closest preset family (`classifyHsl()`, exported for testing). Returns `null` — never a guess — when the logo can't be read or its color is too neutral to signal a brand family.
- `select-theme.ts`:
  - `pickStoredOrLogoTheme(business)` — Steps 3 (reuse) + 1 (logo), shared by both paths below; never calls OpenAI.
  - `pickThemeViaOpenAi(business)` — Step 2 (no logo, no stored preference). Sends brand personality signals (industry, description, brand tone, differentiators, notes) plus each preset's name/`bestFor` list to OpenAI, constrained via `zodResponseFormat` to an enum of `THEME_NAMES` — the model literally cannot return anything outside the 10 approved names, let alone a color.
  - `resolveBusinessTheme(business)` — full selection for real AI generation: stored/logo, else OpenAI.
  - `resolveBusinessThemeForSeed(business)` — selection for the free, no-cost seed-preview path: stored/logo, else a deterministic `INDUSTRY_THEME_DEFAULTS` map (`industry-defaults.ts`, derived from each preset's `bestFor` list). Never calls OpenAI, so "Create test preview" stays free and instant.
- Both `generateWebsiteAction` and `createSeedPreviewAction` persist a newly resolved theme back onto the `Business` record (only when `business.theme` was previously unset) so every future regeneration reuses it — Step 3 of the spec.

### Deferred

- **Firecrawl re-detection**: when a scan discovers an existing logo/branding, compare it against the current theme and auto-switch + regenerate if it differs significantly. Still not implemented — genuinely out of Stage 13's actual scope (which deliberately never auto-changes `theme`/colors/typography — see "Themes and images" in `implementation.md`, Stage 13), not merely deferred for lack of a stage to attach it to.
- Logo color detection is an average-pixel approximation, not a true dominant-color histogram; good enough for family classification (which hue band a logo falls into), not exact-shade matching.

## Photo slot assignment

**Implemented 2026-07-14.** Uploaded business photos (`Business.photoUrls`) are auto-assigned to four template image slots by upload order — hero background, About Us section, WhyChooseUs section, and the featured service card — each preferring a distinct photo and falling back to reusing an earlier one when fewer than four were uploaded. This is a positional guess with no way to know whether a given photo actually suits a given slot (e.g. an odd crop that works for "About Us" can look awkward as a full-bleed hero background).

- `resolvePhotoSlot(override, ...autoFallbacks)` (`lib/ai/generate-preview.ts`) is the single resolution point: an explicit override wins outright; the reserved value `'none'` forces that slot's non-photo fallback (hero's gradient/pattern, About/WhyChooseUs's decorative box, or Services' `picsum` `DEV_FIXTURE`) even though photos exist; otherwise the first defined value in the automatic upload-order chain is used.
- `Business.heroPhotoUrl` / `aboutPhotoUrl` / `whyChooseUsPhotoUrl` / `servicesPhotoUrl` — optional per-slot overrides, each either a URL from the business's own `photoUrls` or the literal `'none'`. Left unset ("Auto"), the automatic assignment applies.
- Admin UI: `PhotosForm.tsx`'s "Photo Assignment" section — a numbered thumbnail grid of the business's uploaded photos plus one `<select>` per slot (labeled "Desktop hero image" / "About Us section" / "Why Choose Us section" / "Featured service card"; Auto / No photo / each numbered photo). Only rendered once at least one photo exists (i.e. practically only after at least one photo has already been uploaded, since overrides reference photos that must already have URLs) so admins can correct a specific bad auto-pick without re-architecting the whole upload flow. Reachable from both the wizard's step 2 (`onboarding/photos/page.tsx`, which now stays on itself after an upload specifically so this section becomes visible before advancing to step 3 — see "Admin application" above) and the detail page's "Photos" card. The desktop hero slot shows a static sizing hint plus a live amber warning whenever the currently-*selected* photo isn't within 100px of 1920×1080 or 1600×900px — see "Hero presentation" below for what that means for rendering. `lib/image/hero-dimensions.ts`'s `describeHeroDimensionWarningsForPhotos()` checks every uploaded photo up front at page-render time (not just whichever is currently saved as the override), returning a `Record<photoUrl, warning | null>`; `PhotosForm.tsx` (a client component) tracks the select's current value in local state and looks up that map on every `onChange`, so the warning updates instantly when the admin changes the selection — no save/reload needed, and no photo is ever left unchecked.
- `AboutSection.tsx` (the section literally titled "About Us") previously never rendered any photo at all — it and `WhyChooseUs.tsx` both trace back to the same historically-misnamed `PreviewTheme.aboutImageUrl` field (which actually only ever fed `WhyChooseUs`). Fixed by adding a distinct `aboutSectionImageUrl` field for the literal About section rather than renaming the existing field (avoids another breaking schema change on top of the Brand Theme System's).
- **`Business.heroPhotoUrlMobile` (2026-07-20)** — a fifth photo slot, structurally alongside the four above (`PhotoPickerField` in `PhotosForm.tsx`, `uploadFieldName="heroPhotoFileMobile"`, dual-write in `updatePhotosAction`), but deliberately **not** part of the automatic upload-order assignment chain: `resolvePhotoSlot(business.heroPhotoUrlMobile)` is called with zero auto-fallback arguments, so an unset slot never silently picks an arbitrary uploaded photo for the mobile crop — it falls back to the theme illustration instead, exactly as mobile behaved before this field existed. Independent of the desktop `heroPhotoUrl`/`heroStyle` resolution — a business can show a real photo on mobile with the desktop hero on illustration, or vice versa. See "Hero presentation" above for how `PreviewTheme.heroImageUrlMobile` renders.
- **Hero tier chain rewrite (Phase 1 stock image repository, 2026-07-27)** — the hero slot's automatic resolution moved out of `resolvePhotoSlot`/inline dimension-checking in `lib/ai/generate-preview.ts` and into a dedicated `resolveHeroImages()` (`lib/image/resolve-hero-image.ts`), with a new chain: (1) explicit admin override — unchanged; (2) a Firecrawl-discovered `role: 'hero'` image whose *already-stored* dimensions are within tolerance of 1920×1080 (16:9) — new, reuses `HERO_FULL_BLEED_DIMENSIONS`/`HERO_DIMENSION_TOLERANCE_PX`; (3) a curated stock hero image matched to `Business.industry` — new, see "Stock image CDN" below; (4) theme illustration. The old "first uploaded business photo" auto-fallback tier is **removed** — uploaded photos are hero-selectable only via explicit override now. The about/services/aboutSection slots' own `resolvePhotoSlot` chains are untouched.
- **Desktop and mobile hero images are always independent — never cropped from, or paired with, one another (corrected 2026-07-27, same day, twice).** An earlier version of this stage auto-cropped one uploaded photo into both a desktop and a mobile variant, then (after that was reversed) still modeled a stock "hero set" as one record holding both a desktop and an optional mobile image. Direct product feedback reversed both: the stock image repository is a flat photo gallery — every `StockImage` is exactly one independently-uploaded image (`kind: 'hero'` records add a `variant: 'desktop' | 'mobile'` tag, nothing more), filtered industry → hero/general → desktop/mobile, with a default desktop image and a default mobile image per industry set as two entirely separate actions (`lib/db/stock-images.ts`'s `getDefaultHeroImage(industry, variant)`, called independently for each in `lib/image/resolve-hero-image.ts` — an industry can have a default desktop hero with no default mobile hero, or vice versa). `Business.heroPhotoUrlMobileAuto` (the earlier auto-crop pairing field) was removed from the model/schema entirely before it ever held real data, and `lib/image/crop-hero-photo.ts` was deleted — no cropping happens anywhere in this feature. Mobile resolution's actual rule, applied uniformly across every tier: `heroPhotoUrlMobile === 'none'` forces no mobile photo; an explicit `heroPhotoUrlMobile` override always wins; otherwise a *genuinely separate, independently-uploaded* mobile image is used if one exists for that tier (only the stock tier can have one, via its own independent default-mobile lookup); otherwise mobile simply reuses whatever desktop photo resolved, as a preview — a real photo beats no photo at all, but nothing is ever cropped or paired to produce it. See `build_log.md`, "Stock images admin redesign: a flat photo gallery," for the full record.

- **Stock photo picker (Part 2, 2026-07-27, same day)** — `PhotoPickerField` (`FormFields.tsx`) gained an optional `stockPhotos` prop that renders a new `StockPhotoPickerModal.tsx` ("Explore our stock photos") alongside the existing "upload your own" input, on 5 of the 6 slots in `PhotosForm.tsx` (all except Business logo). Lets an admin browse the curated stock gallery (from "Stock image CDN" above) and hand-pick a specific photo for one business, instead of only ever getting the industry's automatic default. Opens pre-filtered to the slot's own kind/variant and the business's own industry, but every filter stays changeable to browse the whole gallery. Required zero server-action/schema changes — a picked stock CloudFront URL flows through the exact same `choose()`/hidden-input path as picking one of the business's own uploaded-photo thumbnails already does. Both `PhotosForm.tsx` call sites (`businesses/[businessId]/page.tsx`, the onboarding wizard's `photos/page.tsx`) now also fetch `listAllStockImages()` (filtered to `status: 'active'`) and pass it down. Admin-only — no client-facing (business-owner) dashboard exists yet to reuse this component from.
- **Logo & Photos manager (2026-07-21):** the Photos card's top-of-form Logo/Business-photos file inputs (`PhotosForm.tsx`) were replaced by a unified `PhotoManager.tsx` — one thumbnail-grid UI, above the Photo Assignment section, that both displays the current logo (a real thumbnail via `PhotoThumbnail`, not just a "view" text link) and lets an admin upload/replace the logo, add new photos, and delete any photo, all instantly (no "Save" click, no redirect). Fixes three real bugs: the logo never rendered as an image anywhere in the admin; uploading additional photos via the old bulk `photos` field silently *replaced* `Business.photoUrls` instead of appending to it; and the underlying S3 keys were positional (`photos/{n}.ext`), so a re-upload — or, once delete existed, a photo deleted then a later upload — could collide with and overwrite a still-referenced S3 object at the same key. New photo uploads (`appendBusinessPhotos()`, `lib/s3/business-assets.ts`) now key every file with `crypto.randomUUID()` instead of a position, applied everywhere a photo lands in `photoUrls` — the manager's own uploads, the five per-slot direct-upload inputs in `updatePhotosAction`, and `promoteScanImage`'s scan-image-approval path (`enrichment-actions.ts`) — since `Business.photoUrls` is treated as an opaque list of URLs everywhere it's consumed (`resolvePhotoSlot()` never parses a filename), this required no migration. Three new instant Server Actions in `actions.ts` — `addBusinessPhotosAction`, `deleteBusinessPhotoAction`, `updateBusinessLogoAction` (return type `PhotoManagerState = { message?; photoUrls?; logoUrl? }`, since none of them redirect) — dispatched via `useActionState` from `PhotoManager.tsx`, following the same no-redirect, immediately-client-consistent convention `autoSaveWebsiteSectionsAction` already established. `updatePhotosAction` itself narrowed back to its original scope (Photo Assignment slot overrides only) now that bulk logo/photo upload lives in the new actions instead; `lib/s3/business-assets.ts`'s old `uploadBusinessAssets()` (which replaced `photoUrls` wholesale) was removed entirely. Deleting a photo (`deleteBusinessPhotoAction`) also clears any of `heroPhotoUrl`/`heroPhotoUrlMobile`/`aboutPhotoUrl`/`whyChooseUsPhotoUrl`/`servicesPhotoUrl`/`logoUrl` that pointed at it (falling back to Auto), deletes the S3 object (new `deleteAsset()` in `lib/s3/assets.ts` — the `webpresa-vercel-dev` IAM policy already granted `s3:DeleteObject`, confirmed live, so no infra change was needed), and dual-writes the business's latest `SitePreview.theme` for exactly the slot(s) just cleared, mirroring `updatePhotosAction`'s existing dual-write block, so a deleted photo never keeps rendering on the live preview. `PhotosForm.tsx` now holds `photoUrls`/`logoUrl` as local state fed only by `PhotoManager`'s callbacks (never re-synced from props after mount) and keys each Photo Assignment `PhotoPickerField` by its own current server value, so a slot a delete just cleared visually resets instead of silently re-submitting a now-deleted URL on the next "Save Photos".

- **Browser tab icon / favicon (2026-08-23).** Neither admin nor customer had any way to set a favicon — and since most customers don't know what "favicon" means, every user-facing surface says "Browser tab icon" instead. `Business.faviconUrl?: string` + `faviconSource?: 'auto' | 'manual'` (unset/`'auto'` treated identically — no backfill needed). `lib/image/favicon.ts`'s `generateFaviconBuffer()` derives a square icon from a source image via `sharp(...).resize(256, 256, { fit: 'contain', background: transparent }).png()` — `contain`, never `cover`/crop, so a wide wordmark logo is never sliced (tradeoff: a wide logo shrinks a lot once further downscaled to actual ~16-32px browser tab sizes, and a transparent background isn't guaranteed to read well against every browser's tab chrome — accepted as a universal default; the manual override exists for anyone who wants a purpose-made icon instead). Both admin and customer logo-write paths (`updateBusinessLogoAction`, `updateCustomerLogo`) auto-regenerate the favicon from the new logo whenever `faviconSource !== 'manual'`, using `lib/s3/business-assets.ts`'s new `regenerateBusinessFavicon()` (from bytes already in hand) / `regenerateFaviconFromLogoUrl()` (re-reads an existing `logoUrl` from S3 — used when a customer picks an existing photo as their logo rather than uploading a new one, and by "Reset to Auto"); stored at the fixed key `businesses/{id}/assets/favicon.png`, always overwritten in place, same one-object-per-business convention as `logoUrl`'s fixed `logo` key. Manual overrides (`updateBusinessFaviconAction`/`updateCustomerFavicon`) run through this identical pipeline too — not stored byte-for-byte — so output stays consistently square/small regardless of what was uploaded, and mark `faviconSource: 'manual'`, which both logo-write paths and `deleteBusinessPhotoAction`/`deleteCustomerBusinessPhoto`'s existing "clear any slot pointing at the deleted photo" cascade (when the deleted photo was pinned as the logo) now check before ever touching `faviconUrl` — a manual favicon is never silently overwritten or cleared by a logo change. `resetBusinessFaviconAction`/`resetCustomerFavicon` regenerate immediately from the current logo (never lazily) and set `faviconSource: 'auto'`. Rendering: `app/b/[slug]/favicon-icons.ts`'s `resolveFaviconIcons()` feeds `generateMetadata()`'s `icons` field — `faviconUrl` wins, else the raw (unprocessed, possibly non-square) `logoUrl` as a self-healing interim state for a business that has a logo but hasn't triggered generation yet (no backfill script; it upgrades the next time that business's logo is touched), else `undefined` (falls through to the root `app/favicon.ico` convention file, confirmed via the installed Next.js 16.2.10's own docs to be root-only — not overridable per-route any other way). Applies automatically on a connected custom domain too, with no extra code — `proxy.ts` rewrites custom-domain traffic straight into `/b/[slug]`, same route tree.

### Deferred

- No smarter crop/composition awareness beyond `object-top` positioning on people-photo containers (`WhyChooseUs`, `AboutSection`) — a photo with a genuinely bad composition for a given slot still requires an admin to notice and either override the slot or set it to `'none'`.

## Configurable Website-Section System

**Implemented 2026-07-15 (Stage 11.x — a foundation stage inserted before Stage 12).** Replaces the previously fixed page layout with a stored, per-business section configuration. The core architectural principle: **AI must never directly control React components.** A fixed catalog of approved sections is the only bridge between any stored configuration — manual today, rule-based or (later) AI-proposed in future stages — and actual rendered output; the application always validates and renders through a controlled registry, never a database-driven dynamic import.

- `domain/constants/website-sections.ts` — `WEBSITE_SECTION_TYPES` (the 15 approved identifiers: `header`, `hero`, `trustStrip`, `services`, `about`, `whyChooseUs`, `reviews`, `testimonials`, `gallery`, `faq`, `serviceAreas`, `process`, `ctaBanner`, `contact`, `footer`), `REQUIRED_SECTION_TYPES` (`header`, `hero`, `services`, `contact`, `footer` — always render, never disableable through admin controls), `SECTION_CONFIG_VERSION`, and `WEBSITE_SECTION_CATALOG` — the fixed component catalog: per-section `required`, `defaultEnabled`, `defaultVariant`, `variants` (every section currently supports only `['default']` — structurally variant-ready, no variant library built yet), and `defaultOrder`. Lives in `domain/`, not `lib/`, because the Zod schema validates `variant` against this catalog at parse time.
- `domain/models/website-sections.ts` — `WebsiteSectionConfig` (`component`, `enabled`, `order`, `variant`) and `WebsiteSectionsConfig` (`sectionConfigVersion`, `sections[]`). Stored on `Business.websiteSections?` (`domain/models/business.ts`) — a business-level setting, not a per-`SitePreview` one, so it persists across every "Generate Website" regeneration exactly like `Business.theme` already does (see "Brand Theme System" above), and is the natural shape for the future client dashboard to edit directly.
- `domain/schemas/website-sections.schema.ts` — `WebsiteSectionConfigSchema` (item-level: catalog-enum `component`, boolean `enabled`, bounded non-negative integer `order`, `variant` checked against that component's allowed variants) and `WebsiteSectionsConfigSchema` (whole-config: version not newer than supported, no duplicate `component` entries, every required section present and `enabled: true`). Wired into `BusinessSchema`, so `putBusiness`/`updateBusiness` reject an invalid configuration before it ever reaches DynamoDB.
- `domain/factories/website-sections.factory.ts` — `createDefaultWebsiteSectionsConfig()` builds a full config straight from the catalog, chosen to exactly reproduce the pre-existing fixed template's appearance (`trustStrip`/`whyChooseUs`/`about`/`serviceAreas`/`ctaBanner` default enabled, matching what the old hardcoded template always attempted to render; `reviews`/`testimonials`/`gallery`/`faq`/`process` default disabled, since the old template never rendered them). `Business.websiteSections` being absent — true for every business that predates this stage — is a fully valid state; no migration was run or is needed.
- `web/lib/website-sections/` (mirrors the `lib/theme/` split — business-rule logic, not pure catalog shape):
  - `availability.ts` — `computeSectionAvailability({business, content, hasCta})`, deterministic content-presence checks, no AI, no invented facts. `gallery` reads the existing `Business.photoUrls` (functional today); `reviews`/`testimonials`/`faq`/`process` read new, currently-unpopulated `Business` fields (`googleRating`/`googleReviewCount`/`testimonials`/`faqItems`/`processSteps` — see "Section eligibility signals" below); `services`/`about`/`whyChooseUs`/`serviceAreas` read the generated preview's `PreviewContent`; `header`/`hero`/`trustStrip`/`contact`/`footer` are always available.
  - `resolve.ts` — `resolveStoredOrDefaultSections(stored)`: the lenient, render-safe pipeline (fall back to computed defaults on absence/future-version; drop malformed or unsupported-variant entries; deduplicate; force-enable/backfill required sections; sort by `order`) — never throws, since it runs on every public page load. `resolveRenderableSections(stored, availability)` additionally filters to sections that are both `enabled` and (for optional sections) available. `resolveSectionWarnings(sections, availability)` — the inverse, surfaced in the admin UI.
  - `recommend.ts` — `recommendWebsiteSections({business, content, hasCta})`: the deterministic, non-AI "Apply Recommended Sections" function. Reuses `computeSectionAvailability`'s predicate directly for each optional section's recommended `enabled` value — the objective's own conservative rule set ("Reviews: enable when a review count is available," etc.) *is* the availability check, so the two are kept identical by construction rather than duplicated and risking drift.
- Rendering (`app/b/[slug]/template/`): `section-registry.tsx` defines `sectionRegistry: Record<WebsiteSectionType, (ctx: SectionRenderContext) => ReactNode>` — the only place a stored section identifier becomes an actual React component, wiring the shared render context onto each existing (heterogeneous-props) component. `GeneratedWebsite` (`template/index.tsx`) resolves availability → resolves the renderable section list → maps it through the registry, in place of the old hardcoded JSX sequence. Five new, minimal components joined the registry for previously-nonexistent sections: `GallerySection`, `ReviewsSection`, `TestimonialsSection`, `FaqSection`, `ProcessSection` — all gated by the same availability checks, so they render nothing until real data exists (only `gallery` has a populated data source today).
- Admin (`app/admin/(dashboard)/businesses/[businessId]/`): a "Website Sections" card — `SectionConfigForm.tsx` (checkbox + up/down reorder buttons per section; required sections rendered locked with a "Required" badge; an inline warning on any enabled-but-currently-unavailable optional section) plus **Apply Recommended Sections** and **Reset to Defaults** quick actions. `saveWebsiteSectionsAction` force-enables required sections server-side regardless of submitted form data and validates strictly via `WebsiteSectionsConfigSchema` before persisting — a malformed submission is rejected outright, never partially saved. Header and Footer are pinned (always first/last, no reorder buttons at all); the other reorderable sections reorder via client-side up/down arrows (`section-order.ts`'s pure `moveSection` helper) rather than a raw numeric order field — an admin never sees or types an order number; it's computed from final row position on save. Replaced the original numeric-input design after direct user feedback that it wasn't usable.

### Reviews/Testimonials merge (2026-07-26)

Direct admin feedback: the standalone `testimonials` section duplicated what an admin actually wanted next to the Google rating summary. `ReviewsSection.tsx` now renders both — the rating summary (unchanged) plus, directly underneath, the business's testimonials (`Business.testimonials`, manual and/or Google-sourced), reusing `TestimonialCard`/`TestimonialsMobileCarousel` unchanged. `computeSectionAvailability`'s `reviews` check was widened to `googleReviewCount >= 1 OR at least one visible testimonial`, so a business with testimonials but no Google rating on file still shows them (previously impossible — the two were gated independently). The admin inline editor's "Reviews" row (previously in `NO_EDITOR_SECTIONS`, no content to edit) now shares the same testimonial-management editor (manual entries, `TestimonialsOrderEditor`, `GoogleReviewsPanel`) the "Testimonials" row used to have; `updateBusinessListFieldAction` takes an explicit `section` param (not just `field`) so saving from either row's editor re-expands the correct row on redirect.

The standalone `testimonials` `WebsiteSectionType` — catalog entry, `TestimonialsSection.tsx` component, and registry mapping — was removed once the merge was confirmed live. `Business.testimonials` (the data), `TestimonialCard.tsx`, `TestimonialsMobileCarousel.tsx`, `GoogleReviewsPanel.tsx`, and `TestimonialsOrderEditor.tsx` are all unaffected — only the section *type* that used to render testimonials on its own is gone. The two `enableWebsiteSection(business, ...)` dual-write call sites (Google Places import auto-enabling testimonials on discovery, and the business detail page's "Import/Refresh Google Reviews" action) now target `'reviews'` instead of the removed `'testimonials'`.

**Backward compatibility:** removing an enum value from `z.enum(WEBSITE_SECTION_TYPES)` would otherwise make `BusinessSchema.parse()` throw on read for any business that already had `testimonials` stored in `Business.websiteSections.sections` (e.g. every business the Google Reviews auto-enable dual-write had already touched) — the strict schema is shared between the read and save paths, and `resolveStoredOrDefaultSections`'s existing render-time leniency (`lib/website-sections/resolve.ts`) runs too late to help, since it never gets a record that failed to parse in the first place. `lib/db/businesses.ts`'s new `parseBusinessItem()` wraps every *read* call site (`getBusinessById`/`getBusinessBySlug`/`getBusinessByGooglePlaceId`/`listBusinesses`/`listAllBusinesses`) — it strips any `websiteSections.sections` entry whose `component` isn't in the current `WEBSITE_SECTION_TYPES` before handing off to `BusinessSchema.parse()`, so a legacy record loads cleanly with the stale entry silently dropped. Write paths (`putBusiness`/`updateBusiness`) intentionally keep calling `BusinessSchema.parse()` directly, unmodified — full strictness for anything persisted going forward. This is a repository-layer analogue of `resolveStoredOrDefaultSections`'s own documented leniency, one layer earlier, since that render-time fallback can't run on a record that never successfully parses.

Also fixed in this pass, unrelated to the merge itself: `app/components/TestimonialAvatar.tsx`'s `next/image` now sets `referrerPolicy="no-referrer"` — Google's photo CDN (`lh3.googleusercontent.com`) was rejecting reviewer-avatar requests carrying a `Referer` header from `localhost`, showing as a broken image in local dev only (a deployed domain's referrer wasn't rejected the same way).

### Inline section content editing (2026-07-17)

  - `updateSectionContentAction(businessId, previewId, section, ...)` — the 8 sections backed by `SitePreview.content` (hero, services, whyChooseUs, about, serviceAreas, gallery, ctaBanner, contact).
  - `updateBusinessListFieldAction(businessId, field, ...)` — the 3 durable `Business` list fields (`testimonials`/`faqItems`/`processSteps`), which had no admin write path at all before this (see "Section eligibility signals" above) but persist across regenerations like `theme` and the photo-slot overrides.

The enable/reorder state (`enabledByType`/`orderedTypes`) is now the sole source of truth; "Save Sections" builds a `FormData` from that state and calls the `useActionState` dispatch function directly (a fully supported, typed call in React 19 — its signature is `(payload) => void`, not form-submission-only).

Trust Strip stays fully static (enable/disable only) — its badges are an intentional anti-fabrication guardrail, not missing content.

### Deferred

- No admin UI to enter `googleRating`/`googleReviewCount` — reserved for Stage 12 (Google Places), not manual entry.

- **Pagination past the first 20 results (2026-08-12), and a field-mask bug that silently defeated it until fixed (2026-08-23).** The original Stage 12 `searchPlacesText()` made a single, unpaginated request — any city/industry combo with more than 20 matches silently lost the rest. Fixed by following Google's `nextPageToken` (`web/lib/google-places/client.ts`'s `searchPlacesText()`) up to Google's own hard ceiling of 3 pages / 60 results (`MAX_TEXT_SEARCH_PAGES`), with the required ~2s delay before requesting each fresh token. **That fix didn't actually work in production**, reported as "a Discover search for a real city/industry combo only ever returns 20 results": `FIELD_MASK` (the `X-Goog-FieldMask` header, listing only `places.*` fields) never included the top-level `nextPageToken` field, and Places API (New) strictly filters the *entire* response by this mask — so Google silently stripped `nextPageToken` from every response, making the pagination loop's `if (!nextPageToken) break;` fire after page 1 every time, capping every search at exactly 20 regardless of how many more places actually matched. Fixed by adding `'nextPageToken'` to `FIELD_MASK`. The existing pagination test suite didn't catch this because its mocks return `nextPageToken` directly in the fake response body, independent of what field mask was actually sent — it validated the loop logic but not the real API's field-mask-driven response filtering; a new assertion now checks the mask itself includes `nextPageToken`.
- **No status queue.** An imported business's `status` is the existing `'pending'` value from `BUSINESS_STATUSES` (`domain/models/business.ts`) — `createBusiness()`'s ordinary default, unchanged by `importSelectedPlacesAction`. Starting Stage 13 enrichment remains a distinct, explicit admin action on the business detail page, not a queue or status Stage 12 populates.
- **Industry mapping.** Google's `primaryType`/`types` taxonomy doesn't line up 1:1 with the fixed `INDUSTRIES` enum, and `Business.industry` is required — `web/lib/google-places/industry-map.ts`'s `GOOGLE_TYPE_TO_INDUSTRY` table provides a best-match guess, and the admin review UI always shows an editable `<select>` (defaulting to that guess, blank when nothing matched) so the admin confirms or overrides it per result before import.

## Firecrawl Website Enrichment

**Implemented 2026-07-18.** Manual, admin-triggered single-page Scrape and generation only — see `build_log.md`, "Stage 13 — Firecrawl Website Enrichment" for the full implementation record, and `implementation.md`, Stage 13, for requirements and acceptance criteria.

### Ownership boundaries

`Business` remains the single canonical record. Firecrawl output is evidence, stored as scan artifacts (`ScanEvent` + S3), never auto-written onto `Business` — the only `Business` fields Stage 13 ever sets are its own pipeline-disposition fields (`enrichmentStatus`, `manualApprovalReason`, `manualApprovalNote`), plus one deliberate carve-out added 2026-08-24: a found email auto-fills `Business.email` when it's currently blank (`runAttempt()` in `enrich-business.ts`, mirroring `generation-context.ts`'s "business wins, snapshot only fills a blank field" convention — never overwrites an already-set email). Reported as: a real business's email was visibly found by a full scan (shown correctly in the admin's "Contact Info Found on Website" card) but required a manual per-business "Apply" click to actually land on the record, which doesn't scale. Phone/address are unaffected — still manual-only via that same card (`FoundContactInfo.tsx`/`applyFoundContactFieldAction`, `enrichment-actions.ts`), which continues to work unchanged (including as an explicit overwrite path for email, if ever needed) — its own "found !== current" filter just naturally stops surfacing email as actionable once this auto-apply has run. `ScanEvent` tracks the execution and outcome of each attempt. `SitePreview` stores the generated output and which scan/generation source produced it (`generationMetadata.source`/`scanId`).

### REST client, not the `firecrawl` npm SDK

`web/lib/firecrawl/client.ts`'s `scrapeWebsite()` is a plain `server-only` `fetch` call against `POST https://api.firecrawl.dev/v2/scrape` (`Authorization: Bearer <apiKey>` from `getFirecrawlSecret()`), mirroring `lib/google-places/client.ts`'s established pattern rather than adding the `firecrawl` SDK as a dependency. Confirmed against the installed `firecrawl@4.30.1` SDK source (not just docs) that this is the actual wire contract. Two deliberate reasons for REST over the SDK: (1) the SDK wraps every error in its own `SdkError`, discarding the raw HTTP response — this app needs the raw `Retry-After` header for bounded retry, which the SDK doesn't expose; (2) it avoids adding `axios` (the SDK's HTTP layer) as a dependency the rest of the codebase doesn't otherwise use. `FirecrawlApiError` categorizes failures (`auth`/`rate_limit`/`timeout`/`provider_error`/`unreachable`/`unknown`), mapped to `ScanFailureCategory` in `enrich-business.ts`.

### Structured extraction inside the one Scrape call

The request's `formats` array includes `['markdown', 'links', 'images', { type: 'json', schema, prompt }]` — the `json` entry runs Firecrawl's own extraction LLM as part of the single Scrape call (confirmed via the SDK's `JsonFormat` type). This is still the single-page **Scrape** operation, never Search/Extract/Crawl, and it means this app's own OpenAI usage stays limited to the existing Stage 11 generation call — no second app-side LLM call does raw-page → structured-fields extraction.

### Normalized enrichment snapshot

`web/lib/firecrawl/normalize.ts`'s `normalizeFirecrawlResponse()` is the only place Firecrawl's untrusted `json` extraction result is trusted at all: parsed with a permissive Zod shape, then capped (array lengths, string lengths), sanitized (HTML/control-character stripping, malformed-URL rejection, deduplication), and re-validated against `WebsiteEnrichmentSnapshotSchema` (`domain/schemas/website-enrichment.schema.ts`) before ever being stored or used. Deterministic — no AI call of its own. Social links are derived both from the model's own `socialLinks` output and from discovered page links matching known social domains.

### Merge precedence

`web/lib/firecrawl/generation-context.ts`'s `buildGenerationContext({ business, snapshot })` is the one explicit merge function: the business's own `servicesOffered`/`serviceAreas`/`differentiators`/`description` win outright whenever non-empty; the snapshot fills in only what the business left blank. `business` is never mutated. This is what lets a Stage 12–imported business (which typically has no Stage 11 inputs filled in yet) get its *first* preview directly from Stage 13, without completing Stage 11 manually first — `lib/ai/generate-preview.ts`'s "no services" guard now checks the merged context, not `business.servicesOffered` alone.

**`differentiators` fallback (2026-07-21):** `WebsiteEnrichmentSnapshot.differentiators` (`string[]`, capped at 8) was added to the same structured-extraction JSON schema/prompt described above — Firecrawl's extraction LLM pulls short "why choose us" phrases (years in business, family-owned/local, licensed/insured, 24/7 availability, awards/certifications, guarantees) only when literally stated on the page, same "do not infer" constraint as every other extracted field. `buildGenerationContext()` now falls back to it exactly like `servicesLines`/`serviceAreaLines` — previously `differentiatorLines` had no snapshot fallback at all (an explicit, now-superseded design choice), which meant a business enriched via Firecrawl but with no manually-typed `Business.differentiators` always got an empty Why Choose Us section regardless of what its own website actually said about itself. Businesses enriched before this change need "Enrich Website"/"Retry" run again to pick up the new field, since their stored `extracted.json` predates it.

### SSRF guard

`web/lib/firecrawl/url-validation.ts`'s `validateOutboundUrl()` is applied to three inputs: the business's website URL before ever calling Firecrawl, Firecrawl's reported final URL before it's trusted as metadata, and every discovered image URL before it's fetched. Requires `http`/`https`, rejects embedded credentials, resolves the hostname via `dns.promises.lookup`, and rejects loopback/RFC1918-private/link-local/the AWS metadata endpoint (`169.254.169.254`)/other reserved ranges for every resolved address (a bare IP literal in the URL is checked directly, without a DNS round trip).

### Website image ingestion

`web/lib/firecrawl/images.ts`'s `ingestScanImages()`: takes Firecrawl's discovered `images` array (capped to 15 candidates), skips anything matching a tracking-pixel/icon URL pattern without fetching it, re-validates each URL through the same SSRF guard, fetches server-side with a manually-followed (max 3 hops, each re-validated) redirect chain, an 8s timeout, and an 8MB size cap enforced via both `Content-Length` and actual bytes read, restricts content type to `image/jpeg` (`image/jpg` is also accepted and normalized to `image/jpeg` — several real-world CDNs send the non-standard value; caught during manual verification, see `build_log.md`)/`png`/`webp`, reads real pixel dimensions via `sharp` (already a dependency — same pattern as `lib/image/hero-dimensions.ts`), and rejects anything under 80px on either dimension as a likely icon/tracking pixel. Role classification (`WebsiteImageRole`: `logo`/`hero`/`service`/`gallery`/`team`/`location`/`unknown`) is a deterministic URL-keyword heuristic — never AI, mirroring `lib/website-sections/availability.ts`'s "no AI" convention. Images at or above 400×300px (or classified `logo`) are `accepted`; smaller real photos are `review_required`; everything else is `rejected` (never fetched/stored at all — the only status with no S3 object). **Both `accepted` and `review_required` images are uploaded** to `scans/{businessId}/{scanId}/images/{imageId}.{ext}` — `review_required` only means "not automatically used by generation," not "discarded," since an admin needs to actually see and potentially promote it (see "Scan-image promotion" below). Capped at 8 auto-*accepted* images per scan (uncapped for `review_required`, bounded only by the 15-candidate ceiling). A single bad candidate never fails the whole scan or the batch.

Every stored image (both statuses) gets a stable public URL via the *existing* asset proxy (`/api/assets/scans/{businessId}/{scanId}/images/...` — see "S3 asset storage" above) rather than a raw bucket or a new public path — the same trust boundary as today's admin-uploaded business photos. Never hotlinks the original discovered URL. Never downloads Google Places photos (Stage 12 never even discovers a photo reference to download). Never *automatically* writes to `Business.photoUrls` — `accepted` images are only ever offered to `generatePreviewContent()` as a lowest-priority photo-slot fallback tier, after admin-uploaded `Business.photoUrls`, via the same `resolvePhotoSlot()` chain Stage 11 already uses (see "AI / OpenAI integration" below). `review_required` images are never auto-used at all.

### Scan-image promotion

**Implemented 2026-07-18**, in response to real usage: after a scan completes, an admin needs an actual way to review and use the images Firecrawl found — not just see that some exist. `promoteScanImage(businessId, scanId, imageId)` (`app/admin/(dashboard)/businesses/[businessId]/enrichment-actions.ts`, an internal helper — not itself a Server Action) is the one shared implementation that promotes a single scan image (`accepted` or `review_required` — `rejected` images have no stored bytes to promote) into the canonical Business photo library:

1. Loads the `Business` and `ScanEvent`, locates the image by `imageId`.
2. Idempotency/limit guards: already-promoted (`image.promotedPhotoUrl` set) short-circuits without duplicating; a business already at the 6-photo cap (matching `BusinessSchema`'s `photoUrls` max) is refused.
3. Fetches the object's bytes from its scan-artifact location via `getAsset()`, then **copies** them (not merely re-points a URL) into `businesses/{businessId}/assets/photos/{n}.{ext}` via `putAsset()` — the same physical prefix and numbering convention (`photos/${photoUrls.length}.${ext}`) `updatePhotosAction`'s direct uploads already use. This keeps every `Business.photoUrls` entry's provenance and lifecycle identical regardless of whether it came from an admin upload or a promoted scan image, rather than leaving some `photoUrls` entries secretly backed by the `scans/` prefix.
4. Appends the new `/api/assets/businesses/...` URL to `Business.photoUrls` and persists via `putBusiness()`.
5. Records the resulting URL back onto the `ScanImageAsset.promotedPhotoUrl` field (persisted on the `ScanEvent`) so the UI can show "already added" and never double-promote.

Returns a plain result (`'added'|'already_added'|'limit_reached'|'not_found'`) rather than redirecting itself, so it can be called from two public Server Actions: `approveScanImageAction` (single image, redirects immediately) and `approveScanImagesAction` (**batch — implemented 2026-07-18**, same day, in response to real usage: reviewing five-plus images one click at a time was tedious). The batch action reads every checked `"{scanId}::{imageId}"` pair from the submitted `FormData` and calls `promoteScanImage` on each **sequentially, never in parallel** — necessary because each call re-fetches `Business` fresh and appends to `photoUrls` by current array length, so a parallel batch would race and silently drop entries. Stops adding once the 6-photo cap is hit but keeps counting the rest as `skipped` rather than erroring the whole batch out.

`ScanImageApprovalGrid.tsx` (client component, shared by both surfaces below) renders the checkbox grid: a "Select all"/"Select none" pair that toggles checkbox `.checked` directly via a form ref (no React-controlled state — the checkboxes stay plain uncontrolled inputs, simpler than lifting per-checkbox state) plus one "Add Selected to Photos" submit. Surfaced in two places, both binding the same `approveScanImagesAction`: the scan detail page (`/admin/scans/[scanId]`, every stored image in the grid) and the business detail page's Photos card (`ScanImageReview.tsx`, listing every not-yet-promoted image across *all* of that business's scans, not just the latest) — an admin can review from whichever page they're already on. The Photos `CollapsibleCard` auto-opens (`defaultOpen`) whenever a business has at least one unpromoted scan image, so a freshly completed enrichment doesn't hide new images behind a click.

### Business logo assignment from Photo Assignment

**Implemented 2026-07-18**, in response to real usage: a business logo discovered via Firecrawl (promoted into `photoUrls` like any other scan image — see above) had no way to actually become `Business.logoUrl`, since the logo has always been a single dedicated field set only by direct file upload (`uploadBusinessAssets`), never derived from `photoUrls`. `PhotosForm.tsx`'s "Photo Assignment" section gained a fifth picker, "Business logo" (`logoPhotoUrl`), reusing the exact same `PhotoPickerField` component as the four existing section slots — but with different semantics: there's no automatic upload-order fallback for a logo the way there is for hero/about/etc., so "Auto" here means "leave the current logo unchanged," not "pick one for me." `resolveLogoUrl()` (`[businessId]/actions.ts`) implements this: unset → keep existing `logoUrl`; `'none'` → clear it; any other value (a URL from `photoUrls`) → become the new `logoUrl`. A fresh logo *file* upload (the existing "Logo" field at the top of the Photos card) still always wins over the picker selection, matching the same precedence the four section-slot pickers already establish for their own direct-upload fields.

### Found-contact-info promotion

**Implemented 2026-07-18**, in response to real usage: a business missing `email` (common for Google Places imports, which have no email field) had its Firecrawl-found email visible only inside the scan detail page's raw "Contact found on page" listing — nothing carried it onto `Business.email` itself, and no code path even used it as a *generation* fallback. Two related fixes:

1. **Generation fallback** (`lib/firecrawl/generation-context.ts`): `buildGenerationContext()` now also resolves `contact: { phone?, email?, address? }` — each field independently business-wins-else-snapshot's-first-found-value, exactly like `servicesLines`/`serviceAreaLines`/`description` already worked. `lib/ai/generate-preview.ts`'s `contact` object (used for both `content.contact` and `buildDefaultCta()`'s channel selection) is now simply `generationContext.contact` instead of being built directly from `business.phone`/`email`/`address` — so a generated preview correctly shows/uses a found email or phone when the business record itself has none, matching the documented merge-precedence rule ("Firecrawl may contribute information absent from the canonical generation context") that the original contact-building code had missed. This is generation-input only; it still never writes back to `Business`.
2. **Explicit promotion to Business** (`applyFoundContactFieldAction(businessId, field, value, redirectTo)`, `enrichment-actions.ts`): mirrors scan-image promotion's pattern for contact fields — `updateBusiness(businessId, { [field]: value })` for exactly one of `phone`/`email`/`address`, only ever from a deliberate admin click. `FoundContactInfo.tsx` (rendered inside the Business Details card) compares the latest completed scan's snapshot's first phone/email/address against the corresponding `Business` field and shows an "Apply" (or "Overwrite," if the business already has a different value) button per differing field; fields that already match are hidden. The Business Details card auto-opens when there's a found value worth reviewing, mirroring the Photos card's `hasPendingScanImageReview` pattern. `lib/firecrawl/snapshot.ts`'s `getLatestSnapshotForBusiness()` (shared helper, reads the most recent `completed` scan's `extracted.json`) backs both this feature and could back future evidence surfaces without re-reading S3 redundantly.

### `/admin/scans`

**Implemented 2026-07-18** (was a Stage-9-era static placeholder). `app/admin/(dashboard)/scans/page.tsx` lists every `ScanEvent` across every business (`lib/db/scan-events.ts`'s `listAllScans()` — plain `ScanCommand` + application-code sort, the same dev-scale tradeoff `listAllBusinesses()` already documents, since no GSI supports a global "every scan, newest first" query). `app/admin/(dashboard)/scans/[scanId]/page.tsx` is the detail view: scan metadata, failure category/message when applicable, the full image grid (real thumbnails for every stored image, "Add to Photos" per image), the complete extracted `WebsiteEnrichmentSnapshot` rendered field-by-field, and signed-URL links to the raw `crawl.json`/`extracted.json` artifacts (`viewRawArtifactAction`, session-checked, key-prefix-checked) since those stay outside the public image proxy.

### No-website and no-usable-images paths

A `Business` with no `websiteUrl` never calls Firecrawl at all: `enrichBusinessWebsite()` immediately writes a `manual_approval_required` `ScanEvent` (`failureCategory: 'missing_website'`) and sets `Business.enrichmentStatus`/`manualApprovalReason`/`manualApprovalNote` to the exact required admin-facing copy. A website that scrapes successfully but yields zero accepted images still completes normally (`enrichmentStatus: 'enrichment_completed'`) — `manualApprovalReason: 'no_usable_images'` is a non-blocking note alongside a real success, not a failure state; generation proceeds with the existing Stage 11 image-free fallback (theme-matched illustration hero).

### Retry semantics

Two tiers, matching the "never retry the same ScanEvent" requirement: (1) bounded inline retry *within* one `running` `ScanEvent` attempt (`lib/firecrawl/retry.ts` — exponential backoff + jitter, honors a numeric or HTTP-date `Retry-After`, capped at `MAX_AUTOMATIC_RETRIES` = 2, only for `firecrawl_rate_limit`/`firecrawl_timeout`/`firecrawl_provider_error`) — this never creates a new `ScanEvent`; (2) `retryEnrichmentScan()`, the admin-triggered cross-attempt retry, which always creates a brand-new `ScanEvent` (`retryOfScanId` + `attempt + 1`) and never transitions the prior `failed` `ScanEvent` back to `running` — enforced by never calling `putScanEvent` on the old record again after it's marked `failed`.

### Concurrency

`hasActiveScan()` queries `listScansForBusiness()` and rejects a new `enrichBusinessWebsite()`/`retryEnrichmentScan()` call (`status: 'conflict'`) whenever a `queued` or `running` `ScanEvent` already exists for that business — checked before any DynamoDB write for the new attempt.

### Admin UI

`EnrichmentSection.tsx` on the business detail page is a plain server component — no client JS needed, since active-scan/retry eligibility is fully determined server-side from already-loaded `scans`/`business` data. Both actions (`enrichment-actions.ts`) redirect back to the detail page with an `?enrichmentResult=` query param rather than returning `useActionState` feedback, since enrichment can take several seconds and has more distinct terminal outcomes (completed, manual approval, conflict, failed) than a simple inline message suits.

## Playwright Screenshots (Stage 14)

**Implemented 2026-07-22, deployed to dev and live-verified 2026-07-23.** The project's first compute infrastructure: an ECR-hosted container-image Lambda, asynchronously invoked from a Vercel Server Action, capturing screenshots of a business's existing website and of its generated preview independently. See `build_log.md`, "Stage 14 — Playwright Screenshots" for the full implementation record, and `implementation.md`, Stage 14, for the requirements this implements.

### Two independent targets, two independent ScanEvents

`existing_site` (`Business.websiteUrl`) and `generated_preview` (the business's current `SitePreview`) are captured by separate admin actions on the business detail page (`ScreenshotsSection.tsx`), each creating its own `ScanEvent` (`provider: 'playwright'`, `operation: 'screenshot'`, `targetType` set accordingly). An active capture for one target never blocks the other. `existing_site` is unavailable (no button shown) when the business has no website; `generated_preview` works even for a business that never had one, since Webpresa still needs a screenshot of the site *it* generated.

### Asynchronous invocation, retries disabled

`web/lib/screenshots/capture.ts`'s `captureExistingSiteScreenshot()`/`captureGeneratedPreviewScreenshot()` create a `queued` `ScanEvent` and fire `@aws-sdk/client-lambda`'s `InvokeCommand` with `InvocationType: 'Event'`, then return immediately — the Server Action never waits on Playwright. The Lambda's own async invocation configuration (`infra/lib/constructs/webpresa-screenshot-lambda.ts`) sets `MaximumRetryAttempts: 0`: AWS never automatically re-invokes on failure, since a naive retry could otherwise race a `queued`→`running` conditional transition into a lease conflict. A hard invocation failure (throws or times out before writing any terminal `ScanEvent` state) goes to a dedicated SQS dead-letter queue (`onFailure` destination, 14-day retention) instead — inspectable, never silently lost. The actual recovery path for a stuck scan is the existing 10-minute staleness check (`isStaleScan()`/`markStaleScanFailed()`), surfaced in the admin UI, not an automatic mechanism.

### Idempotency — conditional DynamoDB updates

Every `ScanEvent` status transition (`web/lib/screenshots/capture.ts`'s repository calls on the app side; `infra/lambda/screenshot-capture/src/aws.ts`'s `conditionalUpdateStatus()` on the Lambda side) is a conditional update: `queued`→`running` only succeeds when the current status is still `queued`; the final terminal write only succeeds from `running`. On load, a `ScanEvent` already in a terminal state causes the Lambda to exit immediately without launching a browser — the concrete guard against Lambda's rare at-least-once duplicate delivery (a real property of async invocation, independent of the disabled retry count).

### The Lambda owns the whole capture lifecycle

The invocation payload is identifiers only — `{ businessId, scanId, targetType, previewId? }` — never a URL. The Lambda re-resolves the actual target from DynamoDB itself:
- `existing_site` → `Business.websiteUrl`, validated through the shared SSRF guard (`web/lib/security/url-validation.ts` — see "Relocated SSRF guard" below).
- `generated_preview` → the `SitePreview.slug`, resolved into a URL via a strict same-origin policy (`infra/lambda/screenshot-capture/src/same-origin.ts`) against the `WEBPRESA_APP_BASE_URL` Lambda environment variable — never the general SSRF guard, since this destination is always Webpresa's own app, never genuinely untrusted.

For each of the two fixed viewports (desktop `1440×1000`, mobile `390×844`), `infra/lambda/screenshot-capture/src/handler.ts` launches a **fresh headless Chromium instance per viewport** — not one shared across both — via `infra/lambda/screenshot-capture/src/browser.ts`'s `launchBrowser()` (`playwright-core`; `--no-sandbox --disable-dev-shm-usage --disable-gpu --single-process --no-zygote`), navigates with a `domcontentloaded`-first wait sequence (never `networkidle`-primary, which is unreliable on real sites with persistent analytics/chat-widget connections), waits briefly for web fonts and a visible body, disables CSS animations, and captures `fullPage: false` only — never a full-page scrolling capture (postcard usability, bounded file size). A 403/429 on the top-level navigation response is treated as a coarse bot-protection signal (`blocked_by_bot_protection`), distinct from a generic load failure. One viewport's failure never aborts the other, including a launch failure itself — each viewport's own outcome — `completed` (with its S3 storage key) or `failed` (with a category/message) — is written to `ScanEvent.captureResults.desktop`/`.mobile`. Overall `ScanEvent.status` is `'completed'` (both), `'partial'` (one — a new terminal status), or `'failed'` (neither). The per-viewport browser launch, `--single-process`/`--no-zygote`, and `HOME=/tmp` (Dockerfile) were all added after real deploy testing — none of the three were needed to pass local Docker/RIE testing, only the real deployed Lambda's read-only filesystem and restricted process namespace — see `build_log.md`, "Stage 14", "Live testing against the real deployed Lambda" for the full diagnosis.

### Draft preview visibility — Lambda-minted capture-token cookie

A `generated_preview` capture of an unpublished draft needs to render `/b/[slug]` without an admin session. The Lambda mints a short-lived, single-purpose JWT (`purpose: 'preview_capture'`, `previewId`, `scanId`, 5-minute expiry) immediately before navigating — never the Server Action, which would risk the token expiring before a delayed/redelivered invocation and would also break the identifiers-only payload contract. The token is delivered as an HTTP-only, `Secure`, `SameSite=Strict` cookie (`__Host-webpresa_capture`), never a URL query parameter (which would leak into request logs, browser history, and referrer headers). `app/b/[slug]/page.tsx`'s `resolvePreview()` checks this cookie as an alternate to an admin session — via `web/lib/capture-token.ts`'s `verifyCaptureToken()` (signature + every claim, not just the signature) plus a live lookup confirming `scanId` still names an actual `queued`/`running` `generated_preview` `ScanEvent` for that exact `previewId`. A new dedicated secret, `webpresa-{env}-capture-token` (`{ signingKey }`), backs the HMAC key — read-only by this Next.js app, mint-only by the Lambda.

### Platform-level access: Vercel Deployment Protection bypass

Discovered live, distinct from the app-level cookie above: Vercel's own Deployment Protection sits in front of the *entire* non-production deployment at the edge, before Next.js or the capture-token cookie logic ever runs — an unauthenticated `generated_preview` navigation was redirected to Vercel's own login page instead of reaching `/b/[slug]` at all. The capture-token cookie can't solve this; it's a platform-level gate, not an app-level one. Fixed with Vercel's own "Protection Bypass for Automation": `browser.ts`'s `newContext()` sends the `x-vercel-protection-bypass` header (plus `x-vercel-set-bypass-cookie: true`) on `generated_preview` navigations only, using a value from the new `webpresa-{env}-vercel-protection-bypass` secret (`{ bypassSecret }`, generated in Vercel's dashboard — not by this platform). Read-only by the Lambda's execution role only; the Next.js app never touches this value.

### Relocated SSRF guard

`web/lib/security/url-validation.ts` (moved from `web/lib/firecrawl/` — same `validateOutboundUrl()` implementation, used unchanged by Stage 13's Firecrawl code and Stage 14's `existing_site` target). The Lambda package (`infra/lambda/screenshot-capture/`) is a fully independent npm project — this repo has no workspace tooling connecting `web/`, `infra/`, and the Lambda — so its own `src/url-validation.ts` is a deliberate, explicitly-documented duplicate of the same logic, not an oversight; the two must be kept in sync by hand if either changes.

### Storage layout

```
scans/{businessId}/{scanId}/existing/desktop.png
scans/{businessId}/{scanId}/existing/mobile.png

scans/{businessId}/{scanId}/preview/desktop.png
scans/{businessId}/{scanId}/preview/mobile.png
```

A new sub-shape of the `scans/{businessId}/{scanId}/...` prefix already reserved since Stage 9 — no `ALLOWED_PREFIXES` change needed in `web/lib/s3/assets.ts`. Screenshots are **not** added to the public `/api/assets/...` proxy — private only, admin-viewable via `getSignedAssetUrl()` (reusing the existing `viewRawArtifactAction` from `/admin/scans/[scanId]/actions.ts`, since it already redirects to a signed URL for any key under `scans/`).

### Infrastructure — first compute construct

`infra/lib/constructs/webpresa-screenshot-lambda.ts` — ECR repository (own name, own lifecycle rule capping stored images at 8), `DockerImageFunction` (3008 MB — not the spec'd-as-typical 3072 MB; this AWS account's Lambda service quota caps container-image functions at the legacy 3008 MB ceiling, confirmed by a failed `cdk deploy` — 180s timeout, reserved concurrency 5 per implementation.md's 2-5 spec (initially deployed without any reservation — this account's total Lambda concurrency quota was 10 at first, and AWS requires ≥10 unreserved account-wide after any reservation, leaving no room for one; restored once the account's quota was raised to 1000 — conditional-transition idempotency remains the primary guard against double-execution regardless) — **no VPC** — this Lambda only calls public websites/the public preview URL plus AWS APIs that don't need VPC placement, so attaching one would add a NAT Gateway for no benefit), an explicit `LogGroup` (14-day retention — CDK's construct default is unbounded), and the `EventInvokeConfig` described above. Least-privilege IAM is written as explicit `PolicyStatement`s where CDK's convenience grant helpers turned out to be broader than needed: `Table.grant()` for exactly `dynamodb:GetItem` (Businesses, SitePreviews) and `GetItem`+`UpdateItem` (ScanEvents) matched the spec directly, but `Bucket.grantPut()` does **not** — it grants `PutObjectTagging`/`PutObjectLegalHold`/`PutObjectRetention`/`PutObjectVersionTagging` and an `s3:Abort*` wildcard (covering `AbortMultipartUpload`) alongside `PutObject`, confirmed via a real `cdk diff` against the dev account. Replaced with an explicit statement granting exactly `s3:PutObject`, scoped to the two screenshot prefixes.

`infra/lib/stacks/screenshot-stack.ts` (`WebpresaScreenshotStack`) depends on `WebpresaDataStack` via typed constructor props (`businessesTable`, `sitePreviewsTable`, `scanEventsTable`, `assetsBucket`, `captureTokenSecret`, all now exposed as public readonly fields on `WebpresaDataStack`) — not a string-based cross-stack lookup.

### Image build — deliberately separate from `cdk deploy`

`DockerImageCode.fromEcr(repository, { tagOrDigest })` references a pre-built, pre-pushed image by tag — chosen over `DockerImageCode.fromImageAsset()` (which would have CDK silently build-and-push to its own bootstrap-managed repo on every `cdk deploy`) specifically so this stage has an explicit, inspectable build/push step (`infra/scripts/build-and-push-screenshot-lambda.sh`) rather than an implicit one. **No image has been pushed yet** — `cdk deploy` for the screenshot stack will fail at Lambda creation until the script has been run at least once for the target environment.

### Dockerfile — base image, and two version-pin lessons learned the hard way

Base image `mcr.microsoft.com/playwright:v1.49.0-noble` ships Chromium plus every OS dependency it needs. `aws-lambda-ric` (the Lambda Runtime Interface Client) has a native component requiring `cmake`/`build-essential`/`autoconf`/`automake`/`libtool`/`python3-setuptools` (the last for a `distutils` shim `node-gyp`'s bundled version needs against Python 3.12) — none present in the base image by default, all installed via `apt-get` in the Dockerfile. Two real bugs were only caught by actually building and running the image locally (not by `tsc --noEmit`, which doesn't check runtime module/version compatibility):
1. **`jose` v6 is ESM-only** — a plain `import`/`require('jose')` fails at runtime (`ERR_REQUIRE_ESM`) once compiled to CommonJS. A plain `await import('jose')` doesn't fix it either — `tsc` silently downlevels dynamic imports back into `require()` when targeting `module: commonjs`. The working fix (`infra/lambda/screenshot-capture/src/capture-token.ts`) is `new Function('return import("jose")')` — a runtime-constructed import expression `tsc` cannot statically rewrite.
2. **`playwright-core` must be pinned to the exact base-image browser version**, not a caret range — `^1.49.0` resolved to `1.61.1` at `npm install` time, and Chromium launch failed (`Executable doesn't exist at ...`) against the older browser build baked into the `v1.49.0-noble` image. Fixed by pinning `playwright-core` to an exact, unranged `1.49.0` in `package.json`.

## AI Website Scoring (Stage 15)

Scores a business's **existing website** (never the generated preview — see "scope note" below) using evidence Stages 12–14 already gathered, plus one multimodal OpenAI structured-output call. Runs as a Next.js Server Action, same execution model as Stage 13 — no new AWS infrastructure. Never automatically triggered by Stage 14 completing, same manual-workflow philosophy as every prior stage.

### Scope: existing site only, requires a completed Firecrawl scan

Stage 14 introduced two independent capture targets (`existing_site`, `generated_preview`), each its own `ScanEvent`. Stage 15 only ever scores the `existing_site` target — a business's existing website is the only thing being evaluated as a sales prospect, so there is nothing meaningful to score on the `generated_preview` side. This holds regardless of timing: `enrichBusinessWebsite` (Stage 13) already generates and persists a preview unconditionally as part of crawling, so a preview is typically already present by scoring time — Stage 15 simply has no reason to score it (corrected here and in `implementation.md` — an earlier version of this note incorrectly assumed no preview existed yet at scoring time). `lib/scoring/score-business.ts`'s `scoreBusinessWebsite()` requires a completed Firecrawl (`operation: 'scrape'`) `ScanEvent` to already exist for the business — a missing or in-progress Firecrawl scan returns `not_eligible` rather than running a content-free assessment.

### Deterministic metrics vs. AI assessment

`lib/scoring/deterministic-metrics.ts`'s `computeDeterministicMetrics()` is a pure function (no I/O) computing the non-AI grounding signals fed into the prompt — website/HTTPS/crawl/screenshot presence, phone/email/social/services/hours/contact-form detection, Google Places rating/review count, business category/city/state. Two fields are explicitly heuristic rather than first-class signals: `firecrawlExtractionConfidence` (Firecrawl reports no confidence value of its own — counts populated snapshot fields) and `hoursDetected`/`contactFormDetected` (keyword/regex matching over crawled text — `Business` never persists structured hours, per the Google Places boundary above). `lib/ai/score-website.ts`'s `scoreWebsite()` then makes one `chat.completions.parse` + `zodResponseFormat` call — same structured-output pattern as `generatePreviewContent` (see "AI / OpenAI integration" below) — with the desktop/mobile screenshots (when available, via short-lived signed S3 URLs) sent as `image_url` content parts alongside the text prompt. Output is re-validated against `WebsiteAssessmentSchema` as defense in depth, same as every other AI call in this codebase.

### Qualification: AI recommendation + deterministic overrides

The AI's own `qualification` recommendation (part of `ScanEvent.assessment`) is not always what lands on `Business.qualification` — `lib/scoring/qualification-rules.ts`'s `applyQualificationOverrides()` is a pure function applying two of the six overrides the original Stage 15 task spec listed: "no website → qualified" and "website unavailable → manual review" (keyed off the business's most recent Firecrawl failure category). The other four ("closed business", "national chain", "government organization", "invalid address") are **not** enforced yet — no field on `Business` persists any of those signals today (Google Places' `businessStatus` is fetched live during discovery but explicitly never persisted, per the boundary above; there is no chain/government classification anywhere in the domain model). The AI can still describe those cases in `assessment.weaknesses`/`executiveSummary`, just without a code-enforced override — a real, documented gap to close once one of those signals is actually captured.

Two shortcuts skip the AI call entirely: no website on file (`ScanEvent` marked `'completed'`, `Business.qualification` forced to `'qualified'`) and a Firecrawl scan that failed as unreachable/blocked/invalid/error-response (`'manual_approval_required'`, forced to `'manual_review'`).

**Blocked/error existing-site fix (2026-07-24):** a real admin-reported case scored a business's website 74/Medium/Qualified despite its existing site actually returning HTTP 403 to the crawler. Root cause: Firecrawl's own API call succeeds even when the *target site* it fetched returned an error — the error only shows up in `data.metadata.statusCode`, often alongside some markdown/title text from a bot-block or challenge page, so `enrich-business.ts`'s content-emptiness check let it through as a `'completed'` scan and OpenAI scored the block page's thin content as if it were the real site. Fixed by checking `data.metadata?.statusCode >= 400` before the emptiness check and failing the scan as a new `website_error_response` category, added to both `score-business.ts`'s and `qualification-rules.ts`'s "website unavailable" shortcut sets — so a blocked/erroring existing site now always routes to `manual_review` without ever reaching the AI call, for every future business, not just this one. See `build_log.md`, "Stage 15 fix — blocked/error existing-site responses were scored as real content."

### Persistence split — same "Business is canonical" boundary Stage 13 established

The full `assessment` (all 12 category scores/explanations/suggested improvements, strengths, weaknesses, missing opportunities, executive summary, top problems, confidence) and `deterministicMetrics` live on `ScanEvent` only. The raw, unvalidated OpenAI response is stored as an S3 artifact (`scans/{businessId}/{scanId}/ai-response.json`, following the `rawArtifactKey`/`extractedArtifactKey` pattern) — audit-only, never read back into the app. Only the rollup — `qualification`, `leadPriority`, `websiteQualityScore` — is written onto `Business`, and only via `updateBusiness`; nothing AI-discovered about the business itself is ever written there. The admin override (`adminReviewedQualification`/`adminReviewedScore`) is a separate pair of fields, never overwriting the AI-produced values, so the original assessment is always recoverable — `app/admin/(dashboard)/businesses/[businessId]/scoring-actions.ts`'s `clearScoreOverrideAction` clears them via `putBusiness` with the keys omitted (never `updateBusiness` with an explicit `undefined` — see that file's doc comment).

### Model choice — deliberately separate from Stage 11's generation model

`lib/ai/client.ts`'s `getOpenAiScoringModel()` reads `OPENAI_SCORING_MODEL` (default `gpt-5.5`), distinct from `getOpenAiModel()`/`OPENAI_MODEL` (Stage 11's cost-optimized `gpt-4o-mini` default) — this output drives real sales-prioritization decisions, so it defaults to a stronger model rather than sharing Stage 11's cost-optimized one.

### Active-scan conflict scoping

Scoped to `provider: 'openai', operation: 'score'` only (mirrors Stage 14's per-target scoping, not Stage 13's business-wide guard) — an in-progress Firecrawl or Playwright scan never blocks a scoring attempt, and vice versa.

## Step Functions Scan Workflow (Stage 16)

Connects Stages 11–15's independently-working operations into one durable, admin-triggered AWS Step Functions **Standard** workflow — `webpresa-dev-scan-workflow` (`infra/lib/stacks/scan-workflow-stack.ts`). This is the first stage that chains prior stages together; every one of them remains independently triggerable exactly as before.

### No Lambda in this stack — HttpInvoke straight into the app

Every task is a `tasks.HttpInvoke` call directly into one of seven new `web/app/api/internal/scan/*` Route Handlers, authenticated via an `events.Connection` (API_KEY auth) rather than a Lambda in between. This was a deliberate pivot from an earlier draft that assumed a Lambda-per-task shape: since every task's job is "call an already-tested `web/lib/*` function," and AWS Step Functions can call an HTTPS endpoint natively, adding Lambda would only have meant more AWS compute surface and a second, thinner copy of logic that already lives in, and is already tested in, the Next.js app. The state machine consequently holds **no DynamoDB, S3, or other-secret IAM permissions at all** — its entire footprint is the one Connection.

### `ScanExecution` — a new record, not an overload of `ScanEvent`

`ScanEvent` (Stage 13) is a per-operation record — one per Firecrawl scrape, one per Playwright capture, one per AI score. A single workflow run spans several of these, so `ScanExecution` (new `scan-executions` DynamoDB table, PK `scanExecutionId`) is a separate record representing one Step Functions execution, referencing the `ScanEvent`s (and the `SitePreview`) it produces by ID rather than replacing or duplicating them. `Business` gained three small denormalized rollup fields (`latestScanExecutionId`, `scanExecutionStatus`, `scanExecutionUpdatedAt`) purely so the admin business list/detail views don't need a second query — distinct from Stage 13's `enrichmentStatus`, which is Firecrawl-specific.

### Internal API authentication — the first service-to-service auth in this repo

No such convention existed to extend: the Stage 14 screenshot Lambda talks to DynamoDB/S3 directly with its own IAM role and never calls into the Next.js app over HTTP (its Vercel-bypass-header behavior is a headless-browser navigation, a different mechanism for a different purpose). `web/lib/internal-auth.ts`'s `verifyInternalRequest()` does a `timingSafeEqual` comparison of a fixed request header (`x-webpresa-internal-secret`) against a new `internal-api` Secrets Manager secret — the same secret the EventBridge Connection is configured to send, so there is nothing to keep in sync by hand.

### Reused vs. new

Every internal API route wraps an existing function unchanged: `crawl` → `enrichBusinessWebsite` (Stage 13, its existing no-website branch already skips Firecrawl, so the same route serves both the "website exists" and "no website" branches of the workflow under two different state names), `score` → `scoreBusinessWebsite` (Stage 15, already self-branches on website presence/availability), `capture-screenshot` → `captureExistingSiteScreenshot`/`captureGeneratedPreviewScreenshot` (Stage 14). `scan-status` and `update-execution` are new but thin (a `getScanEventById` read and a `claimScanExecutionStatus` conditional write, respectively). The one non-trivial extraction: `generate-preview` (the no-website branch's preview generation — neither Stage 13 nor Stage 15's no-website shortcuts generate one) required pulling the admin "Generate Website" button's pipeline out of a private function in `businesses/[businessId]/actions.ts` into a shared `lib/ai/generate-and-save-preview.ts`, so both callers use the identical, already-tested logic rather than two copies.

### Idempotency

`web/lib/db/scan-executions.ts`'s `claimScanExecutionStatus()` is the first atomic conditional-transition primitive on the Next.js side (a `ConditionExpression`-guarded `UpdateCommand`, returning `false` rather than throwing on a lost race) — neither `putScanEvent` nor `updateBusiness` is atomic elsewhere in this codebase. It exists specifically to guard Step Functions Standard's at-least-once task-execution semantics, the same class of problem the screenshot Lambda's own `conditionalUpdateStatus` (`infra/lambda/screenshot-capture/src/aws.ts`) solves for Lambda's at-least-once delivery.

### Screenshot completion — polled, not pushed

Screenshot capture is fire-and-forget from the app's perspective (the Stage 14 Lambda owns the eventual result). The state machine polls via a `Wait(15s) → HttpInvoke(scan-status) → Choice` loop, bounded at 40 iterations (~10 minutes, matching Stage 14's own staleness threshold), then proceeds regardless of the outcome — `scoreBusinessWebsite` already tolerates a missing or failed screenshot scan gracefully, so a stuck screenshot never blocks the rest of the workflow.

### Admin trigger

`app/admin/(dashboard)/businesses/[businessId]/workflow-actions.ts`'s `runScanWorkflowAction`/`rerunScanWorkflowAction` are the only server-side entry points that call Step Functions (`web/lib/stepfunctions/client.ts`, same singleton pattern as `lib/lambda/client.ts`) — the browser never calls it directly. A rerun always creates a new `ScanExecution` (`parentScanExecutionId` + incremented `attemptNumber`), mirroring `retryEnrichmentScan`'s existing pattern for `ScanEvent` — a completed execution is never reset back to `queued`.

## AI / OpenAI integration

**Implemented in the Stage 11 foundation work.** Live-tested against the real OpenAI API — real usage costs apply per generation. Stage 15's scoring call (see "AI Website Scoring (Stage 15)" above) follows the same structured-output pattern via a second, independent model/prompt.

- `web/lib/ai/client.ts` — `server-only` singleton `OpenAI` client, built from `getOpenAiSecret()` (fetched once, cached for the process lifetime via the Secrets layer's own caching). Model is read from `OPENAI_MODEL` (env var, default `gpt-4o-mini`) rather than hardcoded.
- `web/lib/ai/generate-preview.ts` — `generatePreviewContent(business, options?)` makes one structured-output request (`chat.completions.parse` + the `openai/helpers/zod` `zodResponseFormat` helper) covering hero copy, services, tagline, about text, differentiators, CTA button *labels*, font, and hero-style choice, run in parallel with the Brand Theme System's `resolveBusinessTheme(business)` (see above) — theme selection is a separate, independent OpenAI concern that never shares a response schema with content generation.
  - **Design invariant:** contact info, service areas, and CTA *type/destination* are always derived in code from the verified `Business` record — never trusted from the model. The model only supplies CTA labels, which are merged into a type/destination structure computed by `buildDefaultCta()` (same phone-first/email-fallback/hidden-CTA priority used by the CTA system's admin default). An uploaded photo always wins over the model's hero-style pick. Brand colors are never trusted from the model either — see "Brand Theme System" above.
  - Output is re-validated against `PreviewContentSchema` / the theme schema before being returned — defense in depth beyond the API's own schema enforcement.
  - **Stage 13 addition:** the optional second argument, `options.enrichment?: { snapshot, scanImages, scanId }`, is the only change to this function for Firecrawl enrichment — when absent, behavior is byte-for-byte identical to the original Stage 11 path (existing call sites are unaffected). When present, `buildGenerationContext()` (see "Firecrawl Website Enrichment" above) fills prompt-input gaps and `generationMetadata.source` becomes `'firecrawl_enriched'` (vs. the now-explicit `'manual_ai'` default) with `scanId` set. Photo-slot resolution (`resolvePhotoSlot`) gains a third, lowest-priority fallback tier of scan-accepted images, after admin-uploaded `business.photoUrls`.
- `generateWebsiteAction` (`app/admin/(dashboard)/businesses/[businessId]/actions.ts`) — soft-capped at 3 real generations per business; always saves the result as a `draft` `SitePreview`, never auto-published.
- `enrichWebsiteAction`/`retryEnrichmentAction` (`app/admin/(dashboard)/businesses/[businessId]/enrichment-actions.ts`, Stage 13) — call `generatePreviewContent` with enrichment context via `lib/firecrawl/enrich-business.ts`; not subject to the `MAX_AI_GENERATIONS` cap (a separate, unbounded admin action, matching the spec's silence on capping Stage 13 specifically — worth revisiting if real usage warrants a cap later).

## Authentication

### Admin

**Implemented in Stage 7** for the single-admin use case. Completely separate from, and untouched by, the Stage 17 customer authentication below — two different problems (one hardcoded operator credential vs. public self-service accounts) intentionally solved two different ways.

- Public homepage: no authentication
- Admin application: username + scrypt-hashed password from environment variables; JWT issued by `jose`, stored in an HTTP-only `SameSite=lax` cookie
- Session validity: 7 days; secret key rotated via `SESSION_SECRET` environment variable
- Route protection: `proxy.ts` intercepts all `/admin/*` requests before rendering
- Defense-in-depth: admin layout server component also reads the session and redirects if missing
- Server Actions independently verify the session before any DynamoDB write

**Future path:** Migrate to Amazon Cognito User Pool when multiple admin users or role-based permissions are needed — not yet done for admin; Stage 17 below is the customer-facing use of that same future path, arriving first because public self-service accounts (password reset, lockout, email changes) need it now, not later.

### Customer (Stage 17 — Website Claim Flow)

Public, self-service accounts: unknown users sign up, choose passwords, forget passwords, and need account recovery, lockout protection, and email changes — none of which the admin's single hardcoded credential ever needed to solve. Rather than hand-rolling a second password store (which would additionally require building an email-sending pipeline that doesn't exist anywhere else in this repo), customer identity is an **Amazon Cognito User Pool**, provisioned by the new `WebpresaUserPool` construct (`infra/lib/constructs/webpresa-user-pool.ts`) and instantiated inside `WebpresaDataStack` as `customerUserPool`/`customerUserPoolClient`.

- Self-service sign-up, `signInAliases: { email: true }`, `autoVerify: { email: true }` (Cognito emails a confirmation code; `ConfirmSignUp` must succeed before `InitiateAuth` will authenticate the account). `accountRecovery: EMAIL_ONLY`, MFA off.
- User Pool Client: `generateSecret: false` (no `SECRET_HASH` computation needed) and `authFlows: { userPassword: true }` **set explicitly** — CDK's default `authFlows` (when the prop is omitted) does not include `USER_PASSWORD_AUTH`, which every sign-in call here depends on.
- Password auth has no Lambda triggers and never touches the Hosted UI — `web/lib/auth/customer-cognito.ts` calls `SignUp`/`ConfirmSignUp`/`ResendConfirmationCode`/`InitiateAuth`/`ForgotPassword`/`ConfirmForgotPassword`/`ListUsers` directly via `@aws-sdk/client-cognito-identity-provider`, authenticated the same way every other AWS call in this app is (the Vercel IAM user's credentials, scoped to the User Pool ARN — see "IAM" under Secrets Manager above). Every Cognito exception is mapped to a small generic reason code before it ever reaches a Server Action's return value — no Cognito-specific error text reaches the client. **"Sign in with Google" is the exception** — see its own bullet below; it's the only thing that uses the Hosted UI/a Lambda trigger.
- The app still issues its **own** session after a successful Cognito authentication — `web/lib/auth/customer-session.ts`, structurally identical to the admin's `session.ts` (a `jose`-signed JWT in an HttpOnly/`SameSite=lax` cookie), but a completely separate cookie name (`webpresa_customer_session`) and secret (`CUSTOMER_SESSION_SECRET`) so an admin session can never be replayed as a customer session or vice versa.
- **Hard rule:** Cognito's `email_verified` attribute is never read by any authorization or ownership check. Business ownership is decided exclusively by `Business.ownerUserId`, set only by the claim-token consumption transaction (`lib/db/claims.ts`, `consumeClaim`) — email confirmation proves control of an inbox, nothing more.
- A third, even shorter-lived cookie — `webpresa_claim_intent` (`lib/auth/claim-intent.ts`), its own secret again (`CLAIM_ATTEMPT_SECRET` — the env var name predates this rename and was deliberately left alone to avoid another manual Vercel config change) — means only "this browser recently presented a valid claim token for this business," never ownership, authentication, or payment. Signed and purpose-scoped (a JWT carrying `{ purpose: 'claim_intent', claimId, businessId, previewId? }`, 30 minutes), but signing only prevents tampering — the server re-validates the claim's live state, and cross-checks the cookie's `businessId` against the freshly-loaded `Claim`'s own `businessId`, on every use regardless (`completeClaimIntent`/`app/claim/continue/page.tsx`).
- **Token → preview → account creation, not token → form.** Both claim entry points (`GET /claim/[claimToken]`, the QR/email deep link; and `submitClaimTokenAction`, the manual `/claim` form) validate the token, set the claim-intent cookie, and redirect to the business's own public preview (`/b/[slug]`) — never straight to `/claim/continue`. The raw token appears in the URL exactly once and disappears immediately on redirect. The preview page (`app/b/[slug]/page.tsx`) reads the cookie back and computes `hasMatchingClaimIntent = intent?.businessId === business.businessId`, which `ClaimBanner.tsx` uses to choose between two "unclaimed" states: a validated visitor sees "your website preview is ready" with a **Claim my website** button linking directly to `/claim/continue` (no code re-entry); an unvalidated visitor sees a postcard-code prompt linking to `/claim?business={slug}` (contextual only — the redirect target after a successful manual submission always comes from the token's own validated business, never this query param).
- Route protection: `proxy.ts` carries a second, fully parallel branch for `/account/:path*`, alongside the untouched `/admin/:path*` branch. `/claim/*` is deliberately not proxy-protected — it's the public claim entry point, gated by the claim-intent cookie at the page/route level instead.
- `web/lib/auth/customer-authorization.ts` — `requireCustomerSession()`/`requireBusinessOwnership()` (Stage 17), extended by Stage 18 with `requireBusinessAccess()`/`requireActiveSubscription()` — see "Stripe Subscriptions (Stage 18)" below.
- Email sending uses Cognito's own default sender for the MVP (a documented ~50/day ceiling) — migrating to SES-backed email is deferred until real signup volume requires it, not a blocker today.
- **Sign-up collects First Name, Last Name, Phone Number alongside email/password** — sent as `given_name`/`family_name`/`phone_number` standard attributes on the same `SignUpCommand` (`signUpCustomer()`). Deliberately **not** added to `WebpresaUserPool`'s CDK `standardAttributes` prop: changing a Cognito user pool's attribute schema after creation forces CloudFormation to replace the pool (deletes every existing user, mints new `UserPoolId`/`UserPoolClientId`). "Required" for these three is enforced only at the application layer (`SignUpSchema` in `web/app/claim/actions.ts`), not by Cognito's schema — the same asymmetry the password-complexity rule already has. Phone numbers are normalized to E.164 (`toE164UsPhone()`, assumes US) before reaching Cognito. `adminGetCustomerProfileBySub()` (replacing the narrower `adminGetCustomerEmailBySub`) reads all four attributes back in one `ListUsers` call for the admin business page.
- **Business Name / Business Address, also collected at sign-up, are NOT Cognito attributes** and do not touch `Business.name`/`Business.address` (which remain canonical, admin-entered/Google-Places-sourced — see "Business is canonical" elsewhere in this doc). They're stored as `customerSubmittedBusinessName`/`customerSubmittedBusinessAddress`, optional fields on the `Claim` record itself (`recordCustomerSubmittedBusinessInfo()` in `lib/db/claims.ts`) — informational, per-claim, for admin reference only.

**"Sign in with Google"** — a "Continue with Google" button on both `/claim/continue` (signup/claim) and `/account/sign-in` (returning sign-in), backed by Cognito federation rather than a second, hand-rolled OAuth integration. Unlike everything else in this section, this path DOES use a Hosted UI domain and a Lambda trigger:

- `WebpresaUserPool` (`infra/lib/constructs/webpresa-user-pool.ts`) gained a `UserPoolDomain` (Hosted UI), an optional `UserPoolIdentityProviderGoogle` (only created once `EnvironmentConfig.googleOAuthClientId` is non-empty — see `deployment.md`'s "Google federation deployment guidance" for why this is a two-phase deploy), and OAuth config on the *existing* App Client (`oAuth`/`supportedIdentityProviders: [COGNITO, GOOGLE]` — password auth via `USER_PASSWORD_AUTH` is entirely unaffected, it's a separate, non-OAuth auth flow on the same client).
- **Account linking — no duplicate accounts.** The hard requirement was: someone who signs up with a password, then later clicks "Continue with Google" with the same email, must land on the exact same account. Cognito does not do this automatically (a federated sign-in and a native sign-in with the same email become two separate pool users, two separate `sub`s, unless something intervenes). A new Pre Sign-up Lambda trigger (`infra/lambda/pre-signup-link/`, a plain `lambda.Function`, not the Docker-image pattern the screenshot/postcard-render Lambdas use — a ~40-line trigger with one AWS-SDK-only dependency doesn't need a container image) fires on every `PreSignUp_ExternalProvider` event, looks up whether a native (password) user already exists with the same *verified* email via `ListUsers`, and if so calls `AdminLinkProviderForUser` to link the incoming Google identity to that existing user *before* Cognito would otherwise mint a new one. The net effect: the ID token this app receives back always carries the original account's `sub`, so `Business.ownerUserId`/`requireBusinessOwnership()`/the session model needed **zero changes** — ownership was already keyed on `sub`, never email.
- A genuine circular CDK dependency was hit and fixed here: granting the Lambda's role `cognito-idp:ListUsers`/`AdminLinkProviderForUser` scoped to `this.userPool.userPoolArn` creates UserPool → Lambda (via `LambdaConfig`) → the Lambda's IAM policy (CDK's own auto-added `DependsOn`) → UserPool (via the ARN reference) — a real cycle CDK's synth-time validator rejects. Fixed by scoping the grant to `resources: ['*']` with an `aws:ResourceAccount` condition instead of the literal pool ARN — every resource this account owns (including this pool) still satisfies that condition, without creating the dependency edge back to the pool resource itself.
- App-side: `web/lib/auth/google-oauth.ts` (builds the Hosted UI `/oauth2/authorize` URL; exchanges an authorization code for tokens at `/oauth2/token` — plain HTTPS, no AWS SDK, no client secret needed since the App Client has `generateSecret: false`, same reasoning `InitiateAuth` already documents for needing no `SECRET_HASH`), `web/lib/auth/google-oauth-state.ts` (the OAuth `state` param is itself a short-lived signed JWT carrying the post-sign-in `next` path — deliberately not a nonce-plus-cookie pair, one fewer moving part for the same CSRF protection), and two Route Handlers: `app/api/auth/google/start/route.ts` (redirects to Hosted UI) and `app/api/auth/google/callback/route.ts` (exchanges the code, decodes the ID token via the now-shared `lib/auth/decode-id-token.ts`, then branches: a valid `webpresa_claim_intent` cookie present means this is a claim in progress — same `completeClaimIntent()` the password flow uses; otherwise it's a plain returning sign-in — `createCustomerSession()` + redirect to the state's `next`).
- `completeClaimIntent` moved out of `app/claim/actions.ts` (a Server Action file) into a new plain lib module, `web/lib/claim/complete-claim-intent.ts`, specifically so the Route Handler above can call the exact same function a Server Action can — and it now *returns* a `{status, redirectTo}` result instead of calling `redirect()` itself, since `redirect()` from `next/navigation` isn't the right tool inside a Route Handler (which redirects via `NextResponse`). No behavior change for the existing password callers, which just call `redirect(result.redirectTo)` themselves now.
- The "same identity re-authenticates on an already-claimed business" case (e.g. a password user re-visits via Google after linking) needed **no new code** — `consumeClaim()` (`lib/db/claims.ts`) already distinguishes `already_consumed_by_user` from a genuine `conflict`, and `completeClaimIntent` already only treats `conflict` as an error, so the idempotent-retry path Google sign-in exercises more often was already correct.

## Stripe Subscriptions (Stage 18)

**Implemented and deployed to development (2026-07-29).** `webpresa-dev-customer-billing-profiles` and the `stripe-subscription-id-index` GSI on `webpresa-dev-businesses` are live. See `implementation.md`, Stage 18, and `build_log.md` for the full implementation/deployment record and what remains (Stripe test-mode Product/Price objects and a populated `webpresa-dev-stripe` secret) before this can be exercised end-to-end.

**One Stripe Customer per Cognito customer, not per Business.** A customer may own several businesses (Stage 17), and each subscribes independently, but they should share one Stripe Customer rather than minting a new one per Business. The authoritative mapping is a new record, `CustomerBillingProfile` (`userId` → `stripeCustomerId`, one row per customer, ever — see "DynamoDB tables" above), created via a conditional `PutItem` the first time a customer checks out for any Business. This is not a "billing account"/organization concept — it carries no seats, roles, or team semantics, only a single foreign key — and it exists specifically because deriving Stripe-Customer reuse by scanning a customer's other owned Businesses (the naive approach) has no atomic "does one already exist" check and risks creating two Stripe Customers for one person under concurrent first-checkouts. `Business.stripeCustomerId` (the Stage 5/17 placeholder field) remains, but only as a denormalized copy for the existing admin display — the profile is always the authority.

**Business-scoped subscription state lives directly on `Business`**, additively: `plan` (`'basic' | 'growth'`), `subscriptionStatus` (`'active' | 'past_due' | 'canceled'` — the one field authorization and the claim banner read), `stripeRawStatus` (Stripe's raw status, diagnostics only), `currentPeriodEnd`/`cancelAtPeriodEnd` (drive "renews/ends on" UI copy — no separate `entitledUntil` field, since Stripe's own `active` status already spans the full paid period during a scheduled cancellation), `lastStripeEventId`/`lastStripeEventAt`/`lastStripeSyncAt` (diagnostics only, never a write gate — see below), `pendingCheckoutSessionId`/`pendingCheckoutExpiresAt` (a checked-before-reuse in-flight Checkout Session reference), and `termsVersion`/`acceptedTermsAt` (latest subscription-agreement acceptance, not a permanent history). No dedicated `Subscription` table — a Stripe Subscription maps 1:1 to exactly one `Business`.

**Webhook reconciliation is snapshot-first, not event-order-first.** The webhook handler (`POST /api/webhooks/stripe`, the first Route Handler in this repo needing raw-body access) always re-fetches the current Subscription object from the Stripe API rather than trusting only the embedded event payload, and writes that snapshot to `Business` unconditionally — safe to repeat on a duplicate event, safe out of order, because the write is always "what Stripe says is true right now," not a delta. `lastStripeEventId`/`lastStripeEventAt` are recorded for diagnostics only and explicitly do not gate whether a write is applied (an older duplicate event will never equal the most-recently-*stored* event ID, so equality alone can't fully detect duplicates — the safety comes from the write being an idempotent snapshot, not from event-ID tracking). A `billingPurpose` metadata field (`'website_subscription' | 'domain_purchase' | 'domain_renewal'`) is attached to every Checkout Session; the webhook handler ignores anything not tagged `'website_subscription'`, so a future domain-purchase/renewal charge sharing the same `CustomerBillingProfile` Stripe Customer can never be misread as a website-subscription event.

**`trialing` never grants entitlement.** Webpresa never intentionally creates a Stripe trial (the generated preview is the trial), so encountering one is treated as a configuration anomaly to log, not a state to map to `active` — granting paid access on an unintended trial would be a fail-open bug.

**Entitlement**: `requireBusinessAccess(userId, businessId)` (Stage 18, extends Stage 17's `requireBusinessOwnership`) returns `{ mode: 'full' | 'billing_recovery' | 'none', plan? }`; a strict `requireActiveSubscription()` wraps it for call sites needing `'full'` only. `past_due` customers get restricted/read-only access with a billing-recovery banner and a Customer Portal link, never full editing. No `requirePlanCapability()` stub is shipped — the future plan-gated-capability boundary is documented in code comments only, added once Stage 19/20 has a real Basic/Growth feature difference to gate.

New GSI: `stripe-subscription-id-index` on Businesses (PK `stripeSubscriptionId`) — the webhook handler's primary lookup path.

## Customer Website Dashboard (Stage 19)

**Implemented, not yet manually verified against a real dev customer session.** No new AWS resource, secret, or environment variable — this stage is pure application code on top of Stage 17's Cognito session/ownership primitives and Stage 18's entitlement. See `implementation.md`, Stage 19, and `build_log.md` for the full record.

**Routes**: `web/app/app/` (a customer-facing route tree parallel to `web/app/admin/` and `web/app/account/`) — `/app` (portfolio entry, auto-redirects a single-business customer straight to their business), `/app/businesses/[businessId]`, `/website`, `/design`, `/billing`, `/settings`. `app/app/layout.tsx` + `AppSidebar.tsx` is the first shared layout the customer-facing tree has ever had (`/account/*` never got one) — modeled directly on `AdminSidebar.tsx`'s responsive pattern (fixed sidebar `md:`+, `framer-motion` slide-in drawer below it), with a business switcher for customers owning more than one Business. `proxy.ts` gained a third branch (`/app/:path*`) alongside `/admin/*`/`/account/*` — session-check only; per-business, per-mode authorization happens on the page/action, not the proxy, since a `billing_recovery` session still needs to reach `/app` in read-only form rather than be turned away at the edge.

**Authorization**: every page and every customer-scoped Server Action independently calls `requireCustomerSession()` → `requireBusinessOwnership()`/`requireBusinessAccess()`. Mutations uniformly go through `requireActiveSubscription()` (redirects unless `mode === 'full'`); `billing_recovery` may still *view* Overview/Website/Design (read-only rendering) and reach Billing (the recovery surface itself), but every mutating action rejects server-side regardless of what the UI showed. `mode === 'none'` never reaches the editing surface at all — the business home page renders a minimal reactivation card linking back to `/account/claim-status` instead.

**`computeBusinessAccessMode(business)`** (`lib/auth/customer-authorization.ts`) — the pure `subscriptionStatus → BusinessAccessMode` mapping, extracted out of `requireBusinessAccess()` so a second call site (below) doesn't duplicate it.

**Draft/publish safety — the one real gap this stage's authorization inheritance didn't already cover**: every admin content-edit action patches whichever `SitePreview` is currently newest **in place**, even when it's already `published` (correct for a trusted admin — edits go live immediately, by design). A customer must never get that behavior. `ensureDraftPreview(businessId)` (`lib/db/site-previews.ts`) is the fix: returns the current newest preview unchanged if it's already `draft`/`ready`, or clones it into a new `draft` version (`createSitePreview({ ...latest, previousVersion: latest.version })`) if it's `published`/`archived`. Every customer-scoped editing function in `lib/customer-editing/` calls this before patching; admin behavior is completely unchanged. Three website states are derived from this at render time, with no new stored field: **Live** (a `published` preview exists, nothing newer on top), **Draft changes** (a newer non-published preview sits on top of a `published` one), **No live site** (nothing ever published).

**`/b/[slug]`'s `resolvePreview()` gained a customer branch** (`app/b/[slug]/page.tsx`) — previously a `draft`/`ready` preview was visible only to an admin session or a Stage-14 capture-token request; an owning customer previewing their own draft got a 404. Now also checks `getCustomerSession()` → the preview's `Business.ownerUserId` matches → `computeBusinessAccessMode(business).mode ∈ {full, billing_recovery}`. Always passes `isAdmin: false` downstream (confirmed by inspection to gate exactly one thing — the admin-only draft banner in `template/index.tsx` — so nothing else leaks to a customer). This is also what makes the dashboard's embedded `<iframe src="/b/[slug]">` preview work at all: same-origin, so the customer's own httpOnly session cookie authenticates the framed request with no capture-token-style workaround needed.

**Editing surface — reused, not forked.** `lib/website-sections/persist.ts`'s `persistWebsiteSections()` (full 15-entry section-config reconstruct/validate/save) was extracted out of the admin's `actions.ts` (previously module-private) so both the admin's and the customer's Sections tab call the identical validated write path — the one editing primitive genuinely shared byte-for-byte between admin and customer. `lib/forms/indexed-list.ts`/`lib/forms/reorder.ts` (also extracted from admin-only files, which now just re-export them) hold the small generic FormData-array and list-reorder helpers both surfaces need. Every other editing action (business contact info, theme, CTA, per-section preview content, business-list fields, Google-review visibility, photos) has its own implementation under `lib/customer-editing/` — necessarily separate from the admin actions, which are wired to the admin session and can't be called from customer code — but reuses the identical domain schemas and repository functions (`PreviewContentSchema`, `putSitePreview`, `putBusiness`, etc.) the admin action uses, just resolving its target preview through `ensureDraftPreview` instead of trusting whatever the admin page already had loaded.

## Customer Onboarding and Domain Connection (Stage 19.x, Parts 1–2)

**Parts 1–2 implemented, automatically tested, not yet manually verified.** See `implementation.md`, Stage 19.x, and `build_log.md` for the full record. **Part 3 (OpenSRS domain purchase) deployed to dev and manually verified end-to-end against a real PTE purchase (2026-08-29)** — built against **OpenSRS Storefront** (a hosted, reseller-branded checkout product), superseding an earlier draft of Part 3 that targeted OpenSRS's raw reseller API (IP-allowlisted Lambda, XML wire protocol, SQS purchase worker — none of that infrastructure was ever built and none of it ships). A real domain (`ctest.info`) was bought through the full flow — SSO into Storefront with no second account, checkout entirely on Storefront's side, webhook delivered/verified/correlated/processed — reaching `DomainConnection.status: 'connected'` (Vercel already `'verified'`) on the first real attempt. `CustomerDomainProfile`/`DomainPurchaseIntent` tables (the latter with a `storefront-username-index` GSI — see below), a `webpresa-{env}-opensrs-storefront` secret, `web/lib/opensrs/` (thin REST client with OAuth 2.0 client-credentials auth + webhook signature verification), `startDomainPurchaseAction` (Domain step's third choice, SSO-redirects into Storefront with no second customer account), and `app/api/webhooks/opensrs/route.ts` (Storefront webhook → Vercel domain attach → `DomainConnection` creation, reusing Part 2's `reconcileDomainConnection` unchanged from there) are all deployed to dev. Several real corrections were made against actual OpenSRS behavior, not just docs: auth turned out to be OAuth 2.0 client-credentials (a raw API key as a Bearer token gets `401 invalid authentication token`); the webhook payload carries no `external_user_id`/`extuserid` field at all, so correlation was reworked around a deterministic `username` instead; the real signature header is `x-signature` formatted `sha256=<hex>`, not the originally-guessed header/format — see `implementation.md`, Part 3, "Documentation gap," for the full record. Prod untouched — no reseller-side Storefront setup done there, no prod secret populated. Part 4 (final integration/dashboard orientation) is specified but not started.

**Onboarding framework (Part 1)**: a route tree, `web/app/app/onboarding/[businessId]/{,/review,/domain,/publish,/tour}` — since 2026-07-31 (see "Onboarding shell redesign" below) this has its own distraction-free shell, not the dashboard's `AppSidebar`. `CustomerOnboarding` (`domain/models/customer-onboarding.ts`, PK `businessId` directly — no separate generated `onboardingId`, the same pattern `CustomerBillingProfile` already uses for its own natural one-to-one key) tracks `status`/`currentStep`/`completedSteps` (`review → domain → publish → tour`, in that order — Review runs before Domain because the confirmed business name/city/state/service feeds Part 3's future domain-name suggestions). `lib/onboarding/steps.ts` holds the pure step-order/access logic; `lib/onboarding/ensure.ts` is a get-or-conditionally-create helper (`ensureCustomerOnboarding`, mirroring `ensureDraftPreview`'s naming); `lib/onboarding/complete-step.ts` holds the step-completion functions, each of which only ever appends a step and re-derives `currentStep`/`status` — never decides *whether* a step's requirement was met (that's the caller's job). The `publish` step, and therefore the whole record, cannot reach `'completed'` until a real `published` `SitePreview` exists — a customer may exit onboarding early with only a draft (via "Enter my dashboard for now"), but the record then stays `'in_progress'` indefinitely until they actually publish, keeping `'completed'` an honest signal.

**Post-Checkout routing**: `app/app/businesses/[businessId]/page.tsx` (the business home) force-routes a `full`-mode customer into `/app/onboarding/{businessId}` only on the genuine first visit — no `CustomerOnboarding` record exists yet. Once a record exists (whether finished or explicitly left early), every later visit shows a "Finish setting up your website" notice instead of a repeated forced redirect — the distinction matters because "Part 1 ships a complete flow" must not mean "every dashboard visit gets bounced back into the wizard forever."

**Existing-domain connection (Part 2)**: `DomainConnection` (`domain/models/domain-connection.ts`) is a standalone record, keyed directly on `normalizedDomain` — not a generated ID plus a uniqueness GSI. A generated-ID-plus-GSI design cannot prevent two concurrent requests from each creating a record for the same domain (a GSI query and a write under a different key are never atomic together); keying the table on the domain itself and creating with `ConditionExpression: attribute_not_exists(normalizedDomain)` (`lib/db/domain-connections.ts`, `createDomainConnectionRecord`) makes the reservation atomic by construction. `Business.slug` is denormalized onto every `DomainConnection` at connect time specifically so host-based routing (below) resolves in one `GetItem` rather than a domain lookup followed by a business lookup.

`web/lib/vercel/{client,domains,errors}.ts` is a new server-only Vercel Project Domains API client — same shape as `lib/firecrawl/client.ts`/`lib/google-places/client.ts` (plain `fetch`, a typed `VercelErrorCategory` enum, Secrets-Manager-sourced credentials via the new `webpresa-{env}-vercel-api` secret, bounded timeouts). `lib/domains/{normalize,connect,reconcile,routing}.ts` hold the business logic: `normalizeDomainInput`/`isValidDomain`/`isReservedHost` (pure), `startDomainConnection` (preflight → atomic reserve-or-resume → attach to the Vercel project), `reconcileDomainConnection` (`draft → awaiting_dns → verifying → connected → certificate_pending → active`, server-derived from a live provider check on every call — never a client-controlled transition), and `resolveActiveDomainRoute` (the narrow host-routing lookup, below). No `'NS'` record type is ever shown to a customer — this stage never asks for nameserver delegation, which would hand Webpresa control over unrelated DNS records (email, other verification TXTs) on the domain.

**Multi-tenant host routing**: `proxy.ts`'s matcher widened from three explicit path prefixes (`/admin/:path*`, `/account/:path*`, `/app/:path*`) to effectively all paths (`/((?!_next/static|_next/image|favicon\.ico).*)`), since host-based routing needs to see the request hostname on `/` too, which none of the three prefixes covered. `isReservedRoutingHost` short-circuits before any DynamoDB call for the overwhelming majority of traffic (anything on `webpresa.com`/`www.webpresa.com`/`localhost`/a Vercel preview host), so this adds no database round trip to normal requests — only to traffic already arriving on an unrecognized hostname. On a genuine foreign host: the `/admin`, `/account`, `/app`, and `/claim` namespaces fail closed (404) rather than falling through to their normal handlers — Webpresa's own management surfaces must never be reachable by path guess under a customer's domain — everything except the root path falls through unchanged (shared static assets/API routes; no per-business `robots.txt`/`sitemap.xml` yet, deferred as new Stage 8 surface outside domain-connection scope), and `/` internally rewrites to `/b/{slug}` when `resolveActiveDomainRoute` finds an `active` `DomainConnection`, or 404s otherwise.

**Dashboard/settings/admin surfaces**: the business-home page's "View website" link and setup checklist ("Connect your domain") both read the business's current `DomainConnection`; Settings gained a read-only domain-status summary with a "Manage domain" link back into the onboarding domain route (Part 2 does not build a second, separate domain-management surface); the admin business-detail page gained a read-only Domain card (status/registrar/timestamps/failure category) with a manual "Refresh status" action — no domain-assignment/removal control is exposed there, since ownership changes stay a customer/onboarding-side operation. **`www` alias support (fix, 2026-07-31)**: real click-through against `fitreppro.com` surfaced `ERR_CERT_COMMON_NAME_INVALID` on `www.fitreppro.com` — unlike the branch-targeting issue above, this was never a dev-only artifact; it would have hit every real production customer identically. ## Contact Forms and Lead Delivery (Stage 20)

**Implemented, not yet deployed/manually verified.** Wires the "Request Service" modal — present on every published customer website since the template shipped, but frontend-only until now (`RequestServiceForm.tsx` used to simulate submission with a timeout and send nothing anywhere) — to a real backend. See `implementation.md`, Stage 20, for the full requirements record; this section covers what was actually built.

**Originally Growth-plan-only; included in every plan as of the MVP pricing change (2026-08-13, see "MVP pricing: Growth hidden, Basic-only" below).** `hasPlanCapability(access, 'lead_capture')` (`lib/auth/customer-authorization.ts`) is the boundary this gates on — no longer plan-differentiated, only requiring `access.mode === 'full'` (an active, non-past-due subscription).

**2026-08-22 correction — the "Request Service" CTA button and modal now render unconditionally, for every business regardless of subscription status.** The original design (above) also hid the CTA button itself (`resolvePreviewCtaConfig`/`resolvePreviewCta` in `template/cta.tsx` took a `leadCaptureEnabled` flag computed in `app/b/[slug]/page.tsx`, and `RequestServiceModal.tsx`'s `openRequestService()` independently no-opped on the same flag) whenever a business had no active subscription — which meant every freshly imported/prospected business (the default state for a business that hasn't been claimed and paid for yet) silently lost its "Request Service" default secondary CTA, and an admin explicitly configuring one on such a business saw the same silent suppression on both preview and the live site. That was the wrong default: a prospect's preview should look and behave the same as a paying customer's. `leadCaptureEnabled` was removed entirely from the CTA-resolution/render path (`cta.tsx`, `template/index.tsx`, `RequestServiceModal.tsx`, `app/b/[slug]/page.tsx`) — the button and modal are now unconditional. Only actual lead *persistence* stays gated, and only at the one place that matters: `submitLeadAction` (`app/b/[slug]/actions.ts`) independently re-resolves the business from the submitted `slug`, re-checks `hasPlanCapability`, and — for a business without an active subscription — returns the same generic `{ status: 'success' }` as a real acceptance without writing a `Lead` record or sending a notification. The visitor-facing form always appears to work; only paying customers actually receive the lead.

**MVP pricing: Growth hidden, Basic-only (2026-08-13).** Only the $39/month Basic plan is offered at launch — `PlanSelectionForm.tsx` (`/account/claim-status`) now renders only the Basic `PlanCard`, and `PricingSection.tsx`'s marketing-page Growth/$79 upsell blurb was removed. `WEBPRESA_PLANS`, `PLAN_CATALOG.growth`, `resolvePriceId()`, `STRIPE_PRICE_ID_GROWTH`, and the Stripe webhook's plan reconciliation are all untouched and remain fully functional — this is a UI-only removal, reversible by reinstating the plan-selection grid. Lead capture (above) moved from Growth-exclusive to included in every plan as part of the same change.

**Data model** — new `Lead` (`domain/models/lead.ts`/`domain/schemas/lead.schema.ts`) and `webpresa-dev-leads` table (see "DynamoDB tables" above). `status` (owner inbox triage: `new`/`read`/`archived`) and `notificationStatus` (SES delivery outcome: `pending`/`sent`/`failed`) are deliberately independent lifecycles on one record.

**Submission transport is a Server Action, not a Route Handler** (`app/b/[slug]/actions.ts`, `submitLeadAction`) — the first mutation originating from `/b/[slug]`, following Stage 17's `submitClaimTokenAction` (`app/claim/actions.ts`), this repo's only prior "public, unauthenticated visitor submits a form" precedent, down to the same undifferentiated-outcome posture: every non-field-validation rejection (rate-limited, plan-gated, duplicate, honeypot/timing-tripped, unknown slug) returns the identical generic success response a real acceptance does. `RequestServiceForm.tsx` uses `useActionState`, the same pattern `ClaimTokenForm.tsx` established. The form's field was renamed `service` → `serviceNeeded` as part of this — a pre-launch rename, no data ever existed under the old name.

**Spam/abuse pipeline** (`lib/leads/spam-guard.ts` for the pure checks, `lib/db/leads.ts` for the DynamoDB-backed ones): honeypot field, minimum-fill-time check, per-IP and per-business rate limiting, and atomic duplicate-submission-fingerprint suppression. **Cloudflare Turnstile is deferred** — no `TURNSTILE_*` secret exists anywhere in this repo; the pipeline documents in code exactly where a token check would slot in (immediately before field validation in `submitLeadAction`).

**`lib/db/rate-limit.ts` (new) is a small, deliberate refactor of existing code**: Stage 17's `claims.ts` rate-limit-counter implementation (`checkAndIncrementRateLimit`/`buildRateLimitKey`) was table-name-hardcoded; extracted into this table-agnostic module (parameterized by table/partition-key name) so Stage 20's Leads rate limiting doesn't carry a second, independently-drifting copy of security-sensitive logic. `claims.ts`'s own exported functions are now thin wrappers delegating to it — no behavior change, no call-site changes for existing callers (`lib/claim/validate-token.ts`).

**Duplicate-submission suppression** reuses the atomic-conditional-write pattern `domain-connections` established for `normalizedDomain` uniqueness (`ConditionExpression: attribute_not_exists(...)`), never a GSI-query-then-write — a `FINGERPRINT#<hash>` item reserved in the Leads table before the real `Lead` write, TTL'd for cleanup.

**Amazon SES — the first use of SES anywhere in this repo.** Unlike every other third-party integration (OpenAI, Firecrawl, Google Places, Stripe, Lob — all a `WebpresaSecret` + API key), SES authenticates purely via IAM (`ses:SendEmail`), so it deliberately gets **no** Secrets Manager entry — a new least-privilege `SesSendLeadNotifications` statement on the existing Vercel-execution role (`vercel-access-stack.ts`) is the entire credential path. `lib/ses/client.ts` mirrors `lib/db/client.ts`'s singleton-client pattern exactly (explicit static credentials on Vercel, default SDK credential chain locally). Unlike every other CDK-managed resource in this repo, the sending identity itself (domain or address, plus DKIM) is verified manually via the AWS Console rather than a CDK `ses.EmailIdentity` construct — this repo has no Route53-hosted-zone CDK construct to drive DNS-based domain verification, so there was nothing for a CDK resource to automate here regardless of who initiates it.

The IAM statement's resource is a bare `'*'`, not a scoped identity ARN. Real-world testing (2026-08-03) went through two narrower attempts first — a single sending-domain identity ARN, then `identity/*` (every SES identity in the account/region) — and both proved unreliable: `iam simulate-principal-policy` said each should be allowed, and other calls with the identical message occasionally got past IAM entirely (reaching a genuine SES-side `MessageRejected` for an unverified recipient, proof the pattern-matched resource *did* sometimes work), yet the deployed app's calls intermittently still came back `AccessDeniedException` with no code or config change in between. This is a known real-world rough edge with pattern-matched resource ARNs for `ses:SendEmail` — apparently evaluated inconsistently server-side by AWS. A bare `'*'` routes through IAM's simpler "any resource" path instead of pattern matching, and resolved it. SES's own identity verification remains the real security boundary regardless of how wide this IAM resource is — this account can only ever send from identities it has independently verified (`webpresa.com`).

**SES production access — approved 2026-08-13** (AWS case `178644604200524`). Both the dev and prod AWS accounts show `ProductionAccessEnabled: true`; the `webpresa.com` domain identity is independently verified with DKIM signing in each. Real sending quota is live in prod (`50,000/24h`, `14/sec`) — any `Business.email` can now receive notifications, not just the two addresses (`andrew@webpresa.com`, `mudge.andrew+test@gmail.com`) originally verified for sandbox-era testing. See `deployment.md`.

**Notification destination is `Business.email` as-is** — the one canonical, already-editable business contact email (Settings page). This is a deliberate MVP relaxation of "never notify a scraped/unverified address," since that field can originate from Google Places/Firecrawl enrichment; a dedicated, customer-confirmed lead-notification address is deferred, not solved here.

**Delivery is persist-then-inline-send, not a queue.** `submitLeadAction` persists the `Lead` first (must succeed before any response), then awaits a bounded (~5s, `AbortController`-timed) SES attempt via `lib/leads/notify.ts`'s `sendLeadNotificationAndRecordOutcome()` — the one shared implementation every caller that ever attempts this send uses (initial submission, the Cron retry sweep, the admin's manual retry), so "what counts as success" is never defined twice. A notification failure is recorded on the lead itself and never risks the already-durable record. This was a deliberate scope decision against a full SQS+Lambda+DLQ pipeline (the pattern Stage 14's screenshot Lambda already establishes) — considered and rejected as more new infrastructure than sending one email justifies for this stage.

**Retry sweep is Vercel Cron, not EventBridge** — `web/vercel.json` (new; no `vercel.json` existed anywhere in this repo before this stage, despite the repository-layout diagram implying one) schedules `GET /api/internal/leads/retry-notifications` **once daily** (`0 6 * * *`). Originally specified every 15 minutes, but the first real `vercel deploy` attempt failed outright — Vercel's Hobby plan caps cron jobs at once/day, and the project is deliberately staying on Hobby for now; Pro is a one-line schedule change away if that changes. This is a convenience safety net, not a correctness requirement — the lead is always persisted synchronously and the notification is always attempted inline at submission time regardless of the cron; a failed inline send just waits up to 24h for automatic retry instead of 15 minutes, with the admin's manual "Retry notification" button available in the meantime for anything more urgent. Authenticated by a second, parallel verifier, `verifyVercelCronRequest()` (`lib/internal-auth.ts`) — Vercel Cron sends `Authorization: Bearer <CRON_SECRET>`, a different convention than the existing `x-webpresa-internal-secret` header the Step Functions EventBridge Connection sends (`verifyInternalRequest`) — reusing the same `internal-api` secret value rather than provisioning a second secret for one more internal caller. The route scans for leads still `pending`/`failed` with attempts remaining (`listLeadsNeedingNotificationRetry`, a bounded full-table `ScanCommand`, the same dev-scale tradeoff `listAllScans` already documents) and re-attempts each. After 5 daily attempts a lead stays `failed` permanently — there is no dead-letter queue in this design; the admin troubleshooting view below is the failure-recovery path.

**Customer lead inbox** — new `/app/businesses/[businessId]/leads`, a new "Leads" sidebar item (shown to every business regardless of plan, like Billing/Settings already are — the upsell state lives on the page itself for a Basic-plan owner rather than hiding the nav item). Gated by `requireBusinessOwnership` + `hasPlanCapability` — deliberately **not** `requireActiveSubscription`, since a Basic-plan owner should see "upgrade to Growth," not be redirected elsewhere. `lib/customer-editing/lead-actions.ts` holds the mark-read/archive mutations (no customer-facing delete, only archive), following the same auth-in-the-route-level-`actions.ts` / mutation-in-`lib/customer-editing/` split every other customer-editing surface uses.

**Admin troubleshooting view** — a new card on the existing admin business-detail page (`LeadsSection.tsx`, alongside `WorkflowSection`/`EnrichmentSection`/`ScoringSection`), showing every lead's `notificationStatus`/`notificationAttempts`/`lastNotificationError` and a manual "Retry notification" action per failed lead (`lead-actions.ts`, calling the identical shared `sendLeadNotificationAndRecordOutcome()` the Cron sweep uses). Never renders a raw SES payload — `lastNotificationError` only ever holds a short exception name/code, never the provider's raw response.

**Cascade delete** — both the admin's `deleteBusinessAction` and the customer's `deleteCustomerWebsite()` (Settings, Danger Zone) now include Leads in their existing previews/scans/postcards/claims teardown.

**Logging** — no PII (`name`/`phone`/`email`/`serviceNeeded`/`message`) or raw IP ever reaches a log line anywhere in the new code, matching this repo's existing `lib/db/*.ts` convention; SES failures log only the provider's exception name, never the raw response.

## Campaign and QR Tracking (Stage 21)

**Implemented, not yet deployed/manually verified.** Rearchitects QR tracking around `Campaign` → `CampaignRecipient` → `Business`, so a manually created, single-recipient test campaign and a future automated many-recipient mail batch are the same data model — see `implementation.md`, Stage 21, for the full specification this section summarizes.

**Three new records, one clean hierarchy.** `Campaign` (`domain/models/campaign.ts`) is not tied to any single business — it owns `name`/`channel`/`status`/optional `expiresAt` only. `CampaignRecipient` (`domain/models/campaign-recipient.ts`) is the attribution unit: it owns the opaque `campaignCode`, a per-recipient `status` kill switch independent of the parent campaign's, and denormalized `totalScans`/`estimatedUniqueScans` rollups. `ScanHit` (`domain/models/scan-hit.ts`) is a new, permanent per-scan record — deliberately **not** named `ScanEvent`, since that name is already the unrelated Firecrawl/Playwright/OpenAI scrape-and-score record (`domain/models/scan-event.ts`); reusing it would make every future grep for either concept ambiguous.

**Destination defaults to the claim flow, not a manually-typed URL (added 2026-08-03).** `CampaignRecipient.destinationType` is `'claim'` (default) or `'custom'` (the exception, an explicit admin-supplied `destinationUrl`). Adding a recipient with no destination override (`addCampaignRecipientAction`) reuses the business's newest still-`isClaimUsable()` `Claim` if one exists, or issues a new one exactly the way the admin's existing "Generate claim link" action does — storing only `claimId` (a plain, non-secret internal reference), never a raw claim link. This is necessary, not a shortcut: the raw claim token is never persisted in recoverable form after issuance (Stage 17 design), so a literal `/claim/{rawToken}` URL could never be saved on a recipient and reused later. Instead `/r/[campaignCode]` performs the claim-intent step itself at scan time — see "Redirect route" below. A business already claimed when added gets `destinationType: 'claim'` with no `claimId`; the redirect route already knows to just link to the live page in that case.

**Campaign codes are opaque, not claim tokens.** `lib/campaign/code.ts`'s `generateCampaignCode()` follows Stage 17's claim-token approach (Crockford Base32, excludes ambiguous I/L/O/U) but shaped for a URL/QR rather than manual entry: no dash-grouping (the claim token keeps its dash-grouping for readability when typed from a mailed postcard). Both now land on the same 80 bits of entropy (`crypto.randomBytes(10)`) — the claim token was shortened from its original 160 bits on 2026-08-03 after review found 160 bits well beyond any realistic threat model for this class of secret; see `implementation.md`, Stage 17, "Claim-token requirements". The Crockford encoder here is a small, deliberate duplicate of `lib/claim/token.ts`'s rather than a shared extraction — this stage doesn't touch Stage 17 files for a ~15-line pure function. Looked up via the `campaign-code-index` GSI on `webpresa-dev-campaign-recipients`; 80 bits of entropy makes a generation-time collision astronomically unlikely, so — matching the claim-token precedent — no atomic uniqueness transaction is needed at creation.

**Relationship to `Postcard` (Stage 22, Phase 0-1 implemented 2026-08-05).** `Postcard` (`domain/models/postcard.ts`, modeled in Stage 5) originally had its own `campaignCode`/`qrDestination` fields, predating this stage's model. Stage 22 refactored `Postcard` to carry an optional `campaignRecipientId` instead, reading its campaign code/destination from the referenced `CampaignRecipient` — a `CampaignRecipient` **is** "one mailed piece" in this model; `Postcard` is the record of its physical rendering and fulfillment (provider, rendered artifact S3 keys, submission metadata, `mailedAt`, `deliveredAt`), not a second source of truth for its destination. The `postcards` table's GSI was renamed accordingly (`campaign-code-index` → `campaign-recipient-id-index`); it was empty in dev at rename time, so no data migration was needed.

**Redirect route** — `GET /r/[campaignCode]` (`app/r/[campaignCode]/route.ts`), a public Route Handler mirroring `/claim/[claimToken]`'s "validate → record → redirect" shape. The actual logic lives in `lib/campaign/resolve-redirect.ts` (mirroring `lib/claim/validate-token.ts`'s separation from its route): rate-limits per IP-hash, resolves the code via `getCampaignRecipientByCode`, requires both `recipient.status === 'active'` and the parent `Campaign.status === 'active'`. For a `'custom'` recipient the destination is just the stored `destinationUrl`; for a `'claim'` recipient it's always `/b/{slug}`, additionally paired with a signed claim-intent cookie (`signClaimIntent()`, the same function `GET /claim/[claimToken]` calls) whenever the business isn't yet claimed and its referenced `Claim` is still `isClaimUsable()` — re-checked live against the database every time, never trusted from the stored recipient. The route then computes a SHA-256 `visitorFingerprint` from `campaignRecipientId | ipHash | userAgent`, reserves it (`reserveVisitorFingerprint`) to detect a new unique visitor, writes a permanent `ScanHit` (recording the *resolved* destination, not a stored one), updates the recipient's rollups (`recordScanHitRollup`), sets the claim-intent cookie when one was produced, and redirects — forwarding every incoming query parameter except a client-supplied `campaign` (always overwritten with the server-resolved code, so attribution can never be spoofed). Unknown, disabled-recipient, non-active-campaign, and rate-limited codes all redirect to the homepage identically — never distinguished to the caller. Device class/browser family/OS are parsed from the User-Agent via `ua-parser-js` (`lib/campaign/user-agent.ts`, new dependency) — heuristic, never presented as exact.

**Manual entry fallback (added 2026-08-03)** — `GET /r` (`app/r/page.tsx`), a static page coexisting with the dynamic `/r/[campaignCode]` route exactly the way `/claim/page.tsx` coexists with `/claim/[claimToken]/route.ts`, for a postcard recipient who can't scan the QR. Its form (`CampaignCodeForm.tsx`) submits to `submitCampaignCodeAction` (`app/r/actions.ts`), which normalizes the typed input (`normalizeCampaignCodeInput`, mirroring `normalizeClaimToken`) and calls `resolveCampaignRedirect()` **unchanged** — the same function the QR route itself calls, with an empty `incomingSearchParams` and a `requestUrl` built from the `host`/`x-forwarded-proto` headers (no `request.url` inside a Server Action). Deliberately does *not* reuse `/claim` (Stage 17's own manual-entry page for claim tokens) despite its already-polished UX: a `/claim` visit would never become a `ScanHit` (silently undercounting anyone who can't scan), and the raw claim token is only ever available once, at the moment a claim is freshly generated — a recipient whose claim was *reused* has no raw token to have ever printed. `campaignCode`, always permanently stored, has neither problem. `lib/campaign/code-format.ts` (new, split from the `server-only`-guarded `lib/campaign/code.ts` so a client component can import it) holds `normalizeCampaignCodeInput` and `formatCampaignCodeForDisplay` (dash-grouped for display/print only — `AB23-CD45-EF67-GH89` — the stored/looked-up value and QR payload stay dash-free); the admin recipient card now shows the formatted code plus a "no scanner? visit webpresa.com/access" hint.

**`/access` — a friendlier public alias for `/r` (added 2026-08-06).** `app/access/page.tsx` is a plain Server Component doing nothing but `redirect('/r')` (temporary, 307 — not `permanentRedirect()`, since a 308 gets cached aggressively by browsers and would make the alias harder to adjust later). "webpresa.com/r" reads as meaningless shorthand to a customer even though it stands for "redirect" internally, so `/access` — a word a person actually understands — is what's printed on postcards and shown in the admin UI's manual-entry hint; `/r` itself is unchanged and still works directly. **Five misspelling-tolerant siblings** (`/acess`, `/acces`, `/accsess`, `/acesss`, `/aress` — each its own `app/{name}/page.tsx`, same one-line `redirect('/r')`) catch the most likely ways someone fat-fingers "access" typing it in from a postcard; each redirects straight to `/r`, not chained through `/access`.

**Data model / infrastructure** — three new tables (see "DynamoDB tables" below): `campaigns` (PK `campaignId`, no GSI — Scan-based admin list, campaign count stays small under manual creation), `campaign-recipients` (PK `campaignRecipientId`; `campaign-code-index`/`campaign-id-index`/`business-id-index`; TTL `ttl` populated only by its `RATELIMIT#` item shape), `scan-hits` (PK `campaignRecipientId`, SK `sortKey` — no GSI needed, since "recent scans for one recipient" is a single ordered Query on `HIT#` items; a second `FINGERPRINT#<visitorFingerprint>` item shape backs the lifetime unique-visitor estimate, deliberately **never** TTL'd unlike Claims'/Leads' own short-window `FINGERPRINT#`/`RATELIMIT#` items, since this one must persist for the life of the recipient). `lib/db/campaigns.ts`/`campaign-recipients.ts`/`scan-hits.ts` are the repositories; `campaign-recipients.ts`'s rate-limit wrappers delegate to the existing table-agnostic `lib/db/rate-limit.ts`, the same as `claims.ts`/`leads.ts` already do.

**QR rendering** — `GET /api/campaigns/[campaignRecipientId]/qr` (admin-session-gated Route Handler), renders a PNG on demand via `qrcode` (new dependency) from `https://.../r/{campaignCode}`. No S3 storage — regenerated on every request, trivial compute cost; used as both the admin preview `<img>` and the download link.

**Admin UI** — `/admin/campaigns` (list + create), `/admin/campaigns/[campaignId]` (campaign details with an inline status control, recipient list with an add-recipient form, per-recipient status toggle, QR preview/download, scan rollups, and a recent-scans list). "Add recipient" needs only a business — the destination override is a collapsed "Advanced" section, and a freshly auto-generated claim's raw code is shown once (`ClaimSection.tsx`'s existing "copy this now" pattern), consistent with the destination model's `'claim'`-is-default design above. Server Actions in `app/admin/(dashboard)/campaigns/actions.ts`: `createCampaignAction`, `updateCampaignStatusAction`, `addCampaignRecipientAction` (generates the `campaignCode` server-side, auto-provisions or reuses a claim), `updateCampaignRecipientDestinationAction` (the `'custom'` override), `updateCampaignRecipientStatusAction`. No charts, no funnels — counts and a recent-activity list only, per this stage's MVP scope.

**Cascade delete** — `deleteBusinessAction` now also deletes a deleted business's own `CampaignRecipient`s and their full `ScanHit` history, but never the parent `Campaign` record itself, since a campaign may still have recipients belonging to other businesses. **A campaign can also be deleted directly (added 2026-08-08)** — `deleteCampaignAction` (a "Delete" button on `/admin/campaigns/[campaignId]`, `window.confirm`-gated, no modal) cascades through every `CampaignRecipient` the campaign owns and their `ScanHit` history first, then deletes the `Campaign` itself, mirroring `deleteCustomerWebsite`'s children-then-parent cascade shape. Any `Postcard` a deleted recipient generated is deliberately left alone — a dangling `campaignRecipientId` reference is already a valid state in the `Postcard` model (a single-postcard test send has none at all), and a `Postcard` may represent a real, already-submitted-to-Lob mailing that must not silently disappear.

**Manual MVP, automation-ready model.** Stage 21 ships with no automated campaign/recipient creation — an admin creates a `Campaign` and adds one (or a few) `CampaignRecipient`s by hand. Nothing in the redirect route, scan recording, or analytics branches on recipient count, so a later automation stage (bulk business selection → generated recipients/QR codes → postcard rendering → Stage 22 mail submission) needs no restructuring — see `implementation.md`, Stage 21, "Future automation".

## Webpresa Postcard Generation and Lob Fulfillment (Stage 22)

**All 5 phases implemented, deployed to dev, and verified live end-to-end against the real Lob API (2026-08-08) — but the stage is IN PROGRESS, not complete.** Generates a physical postcard from a `CampaignRecipient` (Stage 21), routes it through admin review and approval, submits it to Lob for printing/mailing, and tracks its fulfillment status via Lob's webhooks — see `implementation.md`, Stage 22, "Status" for the two open items blocking close-out (a pending Lob support question about their dashboard-preview rendering, and unfinished postcard-back visual design) and the full specification this section summarizes.

**Phase 0/1 — infrastructure and domain model.** See the Stage 21 section above ("Relationship to `Postcard`") for the `campaignRecipientId` refactor. `postcard-webhook-events` (PK `lobEventId`, `postcard-id-index` GSI) is a new, permanent table — immutable Lob webhook history, never deleted or overwritten, mirroring `ScanHit`'s "durable event + denormalized rollup" split. `Postcard` gained the full rendering/review/submission/fulfillment lifecycle fields (`frontArtifactKey`/`backArtifactKey`/`renderedAt`, `reviewedAt`/`reviewedBy`, `submittedAt`/`costCents`/`failureReason`, `mailedAt`/`deliveredAt`) and a `'submitting'` status — a conditional-write guard state between `pending` and `submitted` for Phase 4's idempotency.

**Phase 2 — rendering pipeline.** A second container-image Lambda (`webpresa-dev-postcard-render`, `infra/lambda/postcard-render/`), mirroring Stage 14's `screenshot-capture` Lambda closely (same Playwright/Chromium base image, same Lambda-launch flags) but calling `page.pdf()` instead of `page.screenshot()`, and invoked **synchronously** (`InvocationType: 'RequestResponse'`) rather than fire-and-forget — no DynamoDB access at all, no dead-letter queue (a synchronous caller already gets the failure directly). It navigates to a new internal, non-admin-session-gated page (`/internal/postcards/[postcardId]/render/[side]`), gated by a new `postcard_render` capture-token purpose (`web/lib/capture-token.ts`, mirroring Stage 14's `preview_capture`) that the Lambda mints immediately before navigating. That page deliberately renders the **exact same** `PostcardFront`/`PostcardBack` components the admin review screen shows live — one template, two callers — with a new `showGuides={false}` prop on `PostcardFrame` so the admin-only safe-zone guide lines and card chrome (border/shadow/rounded corners) never end up baked into the print artifact. `web/lib/postcards/render.ts`'s `renderPostcardArtifacts(postcardId)` invokes the Lambda for both sides, and is called automatically by `createPostcardAction` right after a `Postcard` record is created; it refuses to re-render once a postcard is past `'pending'`.

**Postal ink-free zone confirmed (2026-08-08), a real correctness fix.** Lob's docs confirm they automatically overlay the recipient's address and USPS indicia in a documented 4"×2.375" zone on the back (offset 0.275" from the right edge, 0.25" from the bottom, measured from the bleed edge) and **discard whatever artwork is there** — so `PostcardBack.tsx` no longer draws real address text into the actual print artifact (`showGuides={false}`); it only shows it, dashed-outlined, in the admin preview (`showGuides={true}`) as review context. The recipient's address is instead passed structurally to Lob's API (the `to` field), never as rendered text.

**Phase 4 — Lob submission.** `web/lib/lob/client.ts` is a hand-written `fetch` wrapper, not the official `lob` npm package — confirmed against Lob's live docs that the API is plain HTTP Basic Auth (API key as username, blank password) over simple JSON endpoints at `https://api.lob.com/v1`, so a thin wrapper keeps every request/response shape visible in this repo. `web/lib/lob/submit-postcard.ts`'s `submitPostcardToLob(postcardId)` re-validates `reviewedAt` + both artifact keys + the business's mailing address, then guards against double-submission with `transitionPostcardToSubmitting` (`lib/db/postcards.ts`) — a single-item conditional `pending` → `submitting` write, the same shape as `lib/db/claims.ts`'s `consumeClaim` but scaled to one item since only one `Postcard` is involved. On success: `markPostcardSubmitted` records `providerPostcardId`/`costCents`(if Lob returns one — unconfirmed field)/`submittedAt`. On failure: `markPostcardSubmissionFailed` records `failureReason`. **The `from` (sender/return address) field is deliberately omitted from the request** (2026-08-24 fix) — Lob's docs mark it required only when `to` is international, and Lob prints whatever `from` it receives as a return-address block on the physical mailpiece, which was never wanted (a business's own address should show, not Webpresa's). `web/lib/env/lob-sender-address.ts`, which used to supply this, was removed along with its "sender/return address configured" admin checklist item. This was found live: an earlier fix (commit `d040072`) had removed a duplicate, hand-drawn return-address text from `PostcardBack.tsx`'s own artwork under the belief that was the only source, but Lob's dashboard kept showing a return address on submitted postcards because the API-level `from` field was untouched by that fix. **There is no request-level Lob "test mode" flag** — confirmed against Lob's docs; safety is purely a function of which API key (`test_*`/`live_*`) is configured in the `lob` secret, and only a test key is on file (no payment method exists on this Lob account, a hard Lob restriction on live keys). A "Submit to Lob" button (`[postcardId]/SubmitButton.tsx`) appears on the review page once `reviewedAt` is set.

**Re-render-before-submission (2026-08-23) — the stale-artifact bug.** The stored front/back PDFs were otherwise only ever rendered once, at postcard-creation time (`createPostcardAction`) — nothing re-rendered them afterward even though the admin review page's live preview always looked current (it independently re-renders the same `PostcardFront`/`PostcardBack` components from current data on every page load, a completely separate code path from the stored S3 artifact). Editing the business's site after postcard creation left the *reviewed* preview looking right while the *actually-mailed* PDF stayed frozen at the original capture — physical mail that can't be recalled once sent. Fixed by having `submitPostcardToLob` call `renderPostcardArtifacts` (`lib/postcards/render.ts`) itself, immediately before submission, re-fetching the `Postcard` record afterward for the (possibly-changed) artifact keys before signing the URLs handed to Lob. Must run *before* `transitionPostcardToSubmitting`: `renderPostcardArtifacts` only re-renders while `status` is still `'pending'`. A render failure aborts the submission outright (mapped to `'failed'`, or `'conflict'` if the postcard was concurrently claimed by another submission attempt) rather than silently falling back to the stale artifact — matching the phase's existing "never risk mailing something wrong" posture. Also added a manual **"Regenerate PDF"** button (`CampaignDetail.tsx`'s `RecipientCard`, next to "Override destination") so an admin can refresh the preview-review artifact ahead of approval too, not just have it silently fixed at submission time — reuses the existing `retryRenderPostcardAction`, previously only reachable from the `render_failed` recovery path, disabled once the postcard shows as `'submitted'`.

**Phase 5 — webhook receiver.** `web/app/api/webhooks/lob/route.ts`, structured like the existing `web/app/api/webhooks/stripe/route.ts`: verifies Lob's signature (`web/lib/lob/verify-webhook.ts` — HMAC-SHA256 of `{timestamp}.{rawBody}`, hex-encoded, compared against the `Lob-Signature` header, 5-minute replay tolerance on `Lob-Signature-Timestamp`; all confirmed against Lob's live docs), writes a durable `PostcardWebhookEvent` first (the existing `putPostcardWebhookEvent`'s conditional put on `lobEventId` is the entire dedup mechanism), then updates `Postcard`'s rollup fields via a new `applyPostcardWebhookRollup` only when that write was newly recorded. Returns 200 on recognized-but-irrelevant/unresolvable events (never retried forever), 400 only on signature failure, 500 only on genuine internal errors. `web/lib/lob/status-mapping.ts` maps Lob's event-type strings to the rollup — confirmed directly against the live event-type picker in Lob's own dashboard while creating the real webhook (screenshotted 2026-08-08), which turned out to disagree with this file's original scraped-docs source: `postcard.mailed` **is** real, it just isn't offered for a Test-environment webhook (test postcards are never physically produced/mailed, so live-mailing lifecycle events don't apply there) — `postcard.billed` (Lob bills once a piece is produced) is what test mode actually sends, and both map to `'mailed'` so the code needs no change once a live key is in use; just re-subscribe the Live-environment webhook to `postcard.mailed` at that point. `postcard.failed`/`rejected`/`returned_to_sender` all map to `'failed'`; the remaining confirmed events (`created`, `deleted`, `rendered_pdf`, `rendered_thumbnails`, `in_transit`, `in_local_area`, `processed_for_delivery`, `re-routed`, `international_exit`, `viewed`, `informed_delivery.*`) are recorded in history only, never moving `Postcard.status`.

**Live-verified end to end (2026-08-08).** A real test postcard was generated, rendered (real PDFs, visible in S3 and in Lob's dashboard), approved, and submitted to Lob (`psc_742978167ee8d630`). The webhook received 3 real deliveries (`postcard.created`, `postcard.rendered_pdf`, `postcard.rendered_thumbnails`) — signature-verified, correctly deduped (distinct `lobEventId`s), and correctly left `Postcard.status` at `'submitted'` (all three are informational-only per the mapping above). Status will likely never advance past `'submitted'` on this account until it moves to a live key with a payment method on file, since a free-tier test postcard is never actually billed/mailed by Lob.

**PDF/browser mismatch — fixed (2026-08-08).** The rendered print PDF showed faint rectangular artifacts around several box-shadowed footer elements (the QR card, the OR-divider circle, the access-code pill) that never appeared in the browser preview, despite both rendering from the exact same `PostcardFront`/`PostcardBack` component tree via the "one template, two callers" design above. Root cause: `capturePdf()` (`infra/lambda/postcard-render/src/browser.ts`) never called `page.emulateMedia({ media: 'screen' })` before `page.pdf()` — Playwright's `page.pdf()` renders under `print` CSS media by default, a genuinely different Chromium compositor path than `screen` with known box-shadow/border-radius rendering differences, even though this codebase has zero `@media print` rules anywhere and every postcard was designed/approved purely under `screen` media. Fix was a single `page.emulateMedia({ media: 'screen' })` call added right before `page.pdf()` — no component changes, since forcing `screen` media reproduces the approved browser rendering path by construction. Verified against the real deployed Lambda (not just reasoned about): rebuilt and pushed the container image, force-updated the running function to the new image digest (`aws lambda update-function-code` — pushing to the `:latest` ECR tag alone does not update an already-deployed function, since Lambda resolves and caches the digest at deploy/update time), invoked it directly for both sides of the existing test postcard, downloaded the resulting PDFs from S3, and visually confirmed the artifacts are gone while the QR card's blue border, the OR divider, the horizontal separator, and the access-code pill's shadow all still render correctly.

**Admin UI** — `/admin/postcards` (list) and `/admin/postcards/[postcardId]` (review: front/back preview, click-to-enlarge, approval checklist, Approve button, Submit to Lob button, status timeline), under `web/app/admin/(dashboard)/postcards/`. Generation is reachable per-recipient from the Stage 21 campaign admin UI ("Generate postcard" on each `CampaignRecipient` row), not a separate bulk-selection flow.

## Operational Monitoring, Failure Recovery, and Operations Center (Stage 24)

**Implemented and deployed to both dev and prod, 2026-08-14.** Cross-referenced against the real codebase before implementation — see `implementation.md`, Stage 24, "Architecture corrections" for the eight places the original generic spec didn't match this app's actual architecture (Stripe webhooks had no durable failure record at all, unlike Lob; the `status-index` GSIs are unused and flagged as a hot-partition anti-pattern; Vercel-hosted structured logs have no path into CloudWatch without a log drain this repo doesn't have; etc.). `cdk diff` was reviewed and clean before every deploy, in both accounts.

### Shared structured logging

`web/lib/logging/log.ts`'s `log(fields: LogFields)` — the redaction boundary is the TypeScript type itself: `LogFields` is a closed, explicit set of keys (no `payload`/`headers`/`rawResponse` field exists to put a secret into), and `serializeLogFields()` additionally strips anything at runtime that isn't in that allowlist, so even a caller that bypasses the type can't leak an unexpected field. Single-line JSON to `console.log`/`console.error`/`console.warn` — Vercel captures process stdout/stderr directly, no log shipping added. Generalizes the ad hoc `logSafely()` helper previously duplicated in both `app/api/webhooks/{stripe,lob}/route.ts`; integrated at the highest-value failure/completion points across Firecrawl enrichment, screenshot capture, the scan workflow, AI scoring, lead notifications, postcard render/submission, both webhook routes, and the seven `/api/internal/scan/*` routes (which also generate a per-request `requestId` for log correlation — no persistence, log-only).

### `ScanExecution` staleness detection

`web/lib/workflow/stale.ts`'s `isStaleExecution()`/`markStaleExecutionFailed()` — a genuine gap closed, not a redesign: `ScanEvent` has had `isStaleScan`/`markStaleScanFailed` since Stage 14, but `ScanExecution` had no staleness concept at all, so a Step Functions execution that silently died without ever reaching `RecordFailure` stayed `queued`/`running` forever with no admin-visible recovery path. Mirrors the existing pattern exactly — checked on page render, no cron, 20-minute threshold (above the scan workflow's own ~10-minute bounded screenshot-completion poll, so a legitimately still-running execution is never misclassified). Recovery goes through the existing `claimScanExecutionStatus()` conditional-transition primitive, never a blind overwrite. New `markStaleExecutionFailedAction` in `workflow-actions.ts` mirrors `screenshot-actions.ts`'s `markStaleScanFailedAction`.

### `StripeWebhookFailure` — the one new domain record

Unlike Lob (`postcard-webhook-events` — full, permanent delivery history), Stripe webhook processing had zero durable record of any kind: reconciliation is snapshot-first (see "Stripe Subscriptions (Stage 18)" above), and `Business.lastStripeEventId`/`lastStripeEventAt`/`lastStripeSyncAt` are explicitly diagnostics-only, never gating a write. A failed/malformed Stripe webhook was previously invisible outside raw Vercel logs. New `stripe-webhook-failures` DynamoDB table (PK `id`, **TTL enabled and populated on every item** — ~90 days, deliberately different from Claims'/Leads' TTL, which only ever touches a secondary rate-limit item shape while the real record is preserved indefinitely; here the record itself is meant to expire, since this is a short diagnostic window, not a permanent fulfillment record like Lob's). `domain/models/stripe-webhook-failure.ts` + schema + factory + `lib/db/stripe-webhook-failures.ts` (`put`, bounded-`Scan` `listRecent`) follow the same model/schema/factory/repository quartet every other record uses. Written only from the two existing Stripe webhook failure paths (`invalid_signature`, `processing_failed`) in `app/api/webhooks/stripe/route.ts` — never on a successfully processed event, never the raw request body or signature.

### Screenshot DLQ depth visibility

The screenshot Lambda's dead-letter queue has existed since Stage 14 with zero consumers and zero admin/CLI visibility — `web/lib/sqs/dlq.ts`'s `getScreenshotDlqDepth()` is a read-only `sqs:GetQueueAttributes` check (never `ReceiveMessage`/`DeleteMessage` — this module never drains or consumes DLQ messages) against a new `SCREENSHOT_DLQ_URL` env var, sourced from the CFN output the DLQ has exported since Stage 14 (no CDK change needed for the queue itself). `webpresa-vercel-{env}` gained exactly one new IAM statement (`ScreenshotDlqDepthRead`) for this.

### `/admin/operations`

`web/app/admin/(dashboard)/operations/page.tsx` — added to `AdminSidebar.tsx`'s nav (first item, ahead of Campaigns), inherits the existing `(dashboard)/layout.tsx` session guard automatically like every other admin page.

**Needs Attention aggregation** (`web/lib/operations/needs-attention.ts`) composes existing/lightly-extended repository functions — `listAllScans()`, a new `listAllScanExecutions()` (mirrors `listAllScans()` exactly), `listAllPostcards()`, `listLeadsNeedingNotificationRetry()`, `listRecentStripeWebhookFailures()`, `getScreenshotDlqDepth()` — all bounded `Scan` + app-side filter, deliberately the same dev-scale pattern already established rather than activating the flagged, unused `status-index` GSIs. `manual_approval_required` `ScanEvent`s (e.g. every business with no website) are explicitly excluded — an expected, frequent disposition, not a failure, and including it would flood the page. Each item carries a `recommendedAction` (`safe_retry | requires_configuration_fix | requires_manual_review | investigate`) derived from already-known fields (`isRetryableFailureCategory()`, `ScanWorkflowFailure.retryEligible`, a small `firecrawl_auth`-style auth-category set) — no new heuristics beyond what already exists. Recovery buttons are thin wrappers around **existing** Server Actions only (`retryEnrichmentAction`, `markStaleScanFailedAction`, `markStaleExecutionFailedAction`, `rerunScanWorkflowAction`, `retryRenderPostcardAction`, `retryLeadNotificationAction`) — postcard submission failures and provider-auth/config failures render "View Business" only, no button, since no safe retry path exists for those today (`SubmitButton.tsx` already says a new postcard must be generated).

**Dismiss, added 2026-08-14 at the user's request.** Every Needs Attention item, regardless of `recommendedAction`, also gets a "Dismiss" button (`dismissNeedsAttentionItemAction`, `operations/actions.ts`) so the admin can clear something they've already investigated/handled outside the recovery-button flow. Backed by the new `operations-dismissals` table (`lib/db/operations-dismissals.ts`) — a snooze, not a delete: `aggregateNeedsAttention()` fetches and classifies every item exactly as before, then filters the final list against the dismissed-id set as the very last step, so a dismissal can never suppress the underlying record from being recomputed or hide a genuinely still-open problem forever (the dismissal's own `ttl`, ~30 days, expires and the item reappears if it's still unresolved by then).

**`web/lib/postcards/status.ts`** — `derivePostcardStatus()` extracted out of `CampaignDetail.tsx` (previously page-local) so the campaign admin page and the Operations aggregation share one implementation of the render-failure inference (`status === 'pending' && !frontArtifactKey`) instead of a second, driftable copy.

**Recent Operations** (`web/lib/operations/recent.ts`) — a bounded, capped-at-15 merge of completed scans/executions/postcards from the same already-established list functions above. Lead-delivery events are deliberately omitted — `lib/db/leads.ts` has no "recently sent" query, only per-business and needs-retry queries, and adding one would mean a new GSI for a nice-to-have feed item (see implementation.md's own "omit rather than introduce a bad table scan or unnecessary GSI" guidance).

**Credential expiration** (`web/lib/operations/credential-expirations.ts`) — a static, config-driven list (currently just the Vercel API token, expires 2026-10-29, shared by both environments), checked at page-render time against `resolveRuntimeEnvironment()`'s actual values (`'preview'` for the dev deployment, not literally `'dev'`). A 30-day warning window; empty (nothing rendered) is the normal state.

### CloudWatch — `WebpresaMonitoringStack` (Stage 24)

The first CloudWatch dashboard/alarm resources in this project — every prior stage relied on the raw AWS Console/CLI. New `infra/lib/stacks/monitoring-stack.ts`, wired into `bin/webpresa.ts` after the stacks it references; no `WEBPRESA_APP_BASE_URL` dependency, so (like `WebpresaVercelAccessStack`/`WebpresaStockImagesStack`) it has no dedicated npm script — deployed via a plain `cdk deploy Webpresa{Dev,Prod}MonitoringStack --profile webpresa-{dev,prod}`. **Deployed to both accounts 2026-08-14.**

**Scoped to what's genuinely AWS-native**, a correction found during implementation: the original plan was CloudWatch Logs metric filters over the new structured logs for provider-usage counts and Stripe/Lob webhook-failure alarms — infeasible, because those logs are emitted by Vercel-hosted Next.js code and this repo has no Vercel→CloudWatch log drain (a real, separate infrastructure integration, not something to build opportunistically here). The dashboard/alarms instead cover only Lambda (Errors/Throttles/Duration for screenshot-capture and postcard-render), Step Functions execution outcomes, the screenshot DLQ's depth, and DynamoDB throttled-requests on the four highest-traffic tables (scan-events, scan-executions, postcards, businesses — not all 15) — every one of these already has a real CloudWatch metric with zero new log-shipping work. DynamoDB's `metricThrottledRequestsForOperations()` had to be scoped to exactly the six operations `webpresa-vercel-{env}` is actually granted (`GetItem`/`PutItem`/`UpdateItem`/`DeleteItem`/`Query`/`Scan`) — the unscoped default (all 14 `dynamodb.Operation` values) exceeds CloudWatch's 10-metric-per-alarm math-expression limit, caught by a real synth-time failure while building this stack. Provider usage/cost visibility and Stripe/Lob webhook-failure visibility instead come from `/admin/operations` (DynamoDB-backed, no CloudWatch dependency) and Vercel's own log viewer — see `operations.md`.

9 CloudWatch alarms total (2 screenshot Lambda, 1 postcard-render Lambda, 1 DLQ depth, 1 Step Functions failures, 4 DynamoDB throttle), identical in both dev and prod — no SNS/Slack/PagerDuty target exists in either environment, so a stricter/looser split has no real effect yet; alarms fire and are visible in the CloudWatch console/dashboard only.

**AWS Budget (spend alarm), added 2026-08-14 at the user's explicit request** — one `AWS::Budgets::Budget` (`CfnBudget`, the only construct level this AWS service offers; no L2 exists) per environment, `webpresa-{env}-monthly-spend`, `$25/month` in both dev and prod (`EnvironmentConfig.monthlyBudgetUsd`/`budgetAlertEmail`, `infra/lib/config/environments.ts` — not a secret or account identifier, just a per-environment operational threshold, so it lives alongside every other per-environment value there). Two email notifications per budget: an `ACTUAL` spend breach at 100% of threshold (the real alarm) and a `FORECASTED` breach at 100% (an early heads-up before it happens) — both to the account owner's email. Account-wide, not scoped to Webpresa's own resources specifically (AWS Budgets has no resource-tag-based cost budget granular enough for that without separately-activated Cost Allocation Tags, out of scope here). Confirmed live via `aws budgets describe-budgets --account-id <account> --profile webpresa-{dev,prod}`.

`infra/test/monitoring-stack.test.ts` (15 tests) asserts resource shape, naming, alarm configuration, the budget's threshold/notification shape, and that no SNS resources are created.

`web/docs/operations.md` — 16 failure-mode runbooks (Step Functions failures, the real 2026-08-12 EventBridge-Connection-deauthorized incident, the real stale-capture-token incident, screenshot staleness/DLQ, stale Lambda images, Stripe/Lob webhook failures, Lob submission failures, SES, Vercel API token expiry, OpenAI/Firecrawl/Google Places provider failures, DynamoDB throttling, AWS spend) plus credential-expiration/rotation, each covering Symptoms / Likely cause / How to verify / Safe recovery / Retry-vs-replay-vs-rerun / How to confirm recovery. ## Admin Analytics Dashboard (Stage 29)

**Implemented 2026-08-20.** `/admin/analytics` — business/acquisition/revenue metrics, deliberately separate from `/admin/operations`'s technical/system health. Now the default `/admin` landing page (`AdminSidebar.tsx`'s `NAV_ITEMS` lists it first, ahead of Operations); Operations itself is untouched.

### Domain model additions (no infra change — plain optional attributes on existing items)

- `Business.firstPaidAt?` / `Business.canceledAt?` — set only by `app/api/webhooks/stripe/route.ts`'s existing reconciliation write (same call site as `subscriptionStatus`/`plan`/`billingInterval`), inside the already-fetched `business` object it has in scope. `firstPaidAt` is set once and never overwritten; `canceledAt` reflects only the most recent cancellation, the same snapshot-only semantics `currentPeriodEnd`/`cancelAtPeriodEnd` already have — no subscription-event-history table was added for this MVP.
- `Postcard.templateVariant?` — stamped once at creation (`createPostcardAction`) via the existing `resolvePostcardTemplateVariant(business)`, so a postcard's template-performance row stays stable even if the business's `websiteUrl` changes later. Legacy postcards without it fall back to computing the variant live.
- `PLAN_CATALOG` (`domain/constants/plan-catalog.ts`) gained `monthlyPriceCents`/`annualPriceCents` — the numeric counterpart to its existing display strings, and the sole source MRR math reads from.

### `web/lib/analytics/`

Mirrors `lib/operations/`'s split exactly: `dashboard-types.ts` (client-safe), `date-range.ts`/`calculations.ts`/`attribution.ts` (pure, no `server-only`, no I/O — the full unit-test surface), `dashboard.ts` (`server-only`, `getAnalyticsDashboardData()`, the page's sole entry point, mirroring `aggregateNeedsAttention()`'s role). Reuses the existing bounded-`Scan` pattern (`listAllBusinesses()`, `listAllPostcards()`, `listAllCampaigns()`) rather than the flagged `status-index` GSIs, plus one new `listCampaignRecipientsByIds()` batch-get in `lib/db/campaign-recipients.ts` for resolving the postcard cohort's recipients without a second full scan.

**Funnel** (Postcards Sent → Engaged → Claimed → Signed Up → Paid) is computed from real, already-shipped events: `Postcard.submittedAt` (sent), `CampaignRecipient.estimatedUniqueScans` (engaged — the deduped fingerprint estimate, so repeated scans of one QR don't inflate the count), `Business.status` rank vs. `'claimed'` (claimed — the same event-driven funnel field the just-shipped `advanceBusinessStatus` writes), and `Business.firstPaidAt` (paid, deduped by business). "Signed Up" is documented as literally the same count as "Claimed" — in this architecture, claim consumption and Cognito sign-up happen atomically in `consumeClaim()`.

**MRR trend** reconstructs true active MRR per calendar month-end (not an acquisition-velocity "new MRR by cohort" chart), so it directly answers whether recurring revenue is trending up or down. Known, accepted limitation: a cancel-then-resubscribe cycle appears continuously active through the gap, since only the latest `canceledAt` is retained.

**Template attribution's shared-claim tie-break**: when one reused claim is referenced by two `CampaignRecipient`s for the same not-yet-claimed business (a real path in `campaigns/actions.ts`), only the earliest-created recipient gets "claimed"/"paid" credit in the per-template table, preventing one business's outcome from inflating two templates' conversion rates. The business-level funnel itself stays postcard-indexed and is unaffected.

**Cancellation reasons**: not captured anywhere in this codebase (confirmed — no Stripe `cancellation_details` handling, no survey, no `Business` field). `getCancellationReasons()` always returns a `{ collected: false, breakdown: [] }` placeholder; no field or subsystem was built for unused capture.

**Caching**: `getAnalyticsDashboardData` is wrapped in `unstable_cache` (3-minute revalidation) — deliberately different from Operations' fully-uncached `force-dynamic`, since Operations is incident response (staleness is actively harmful) while Analytics is a reporting page where a few minutes of staleness is normal and the underlying computation (two bounded scans + a batch-get) is worth not repeating on every filter tweak.

### `/admin/analytics` UI

`web/app/admin/(dashboard)/analytics/page.tsx` plus presentational sub-components matching the existing admin design system exactly (bordered white cards, `--color-brand` tokens, the campaigns-table styling) — no chart library exists anywhere in this repo, so the MRR trend and funnel bars are hand-built `<div>`/inline-style bar charts, not a new dependency. `PostcardPerformanceTable.tsx` and `PostcardMapCard.tsx` (see "Postcard Map" below) are the only `'use client'` components (local interaction only, mirroring `NeedsAttentionSection.tsx`'s "thin client wrapper around server-computed data" precedent).

### Postcard Map

A card at the bottom of `/admin/analytics` — one pin per business that has at least one `Postcard` record, colored by funnel stage, with a client-side industry filter and Google Maps pan/zoom. Deliberately **not** "every business," only ones actually mailed — see `computeMapPins` below.

- **`lib/geo/zip-centroid.ts`** — resolves a business's approximate location from `address.postalCode` via the bundled `zipcodes` npm package (ZIP-centroid, not a street-level geocode; no network call, no geocoding API, no new secret). This is a deliberate simplification: `Business` has no stored lat/lng anywhere (the transient Google Places search result's `latitude`/`longitude` are still discarded before a `Business` is persisted, unchanged by this stage), and a free, synchronous, bundled dataset was chosen over provisioning a Google Geocoding API integration for this MVP.
- **`lib/analytics/map-pins.ts`** — `computeMapPins(businesses, postcards)`, pure, called from `computeDashboard()` using the same `allBusinesses`/`allPostcards` arrays already fetched for the rest of the dashboard (no new DB scan). **Color is most-advanced-funnel-stage-wins**: `Business.status === 'cancelled'` → red; `'customer'` → green; `'engaged'` or `'claimed'` → purple; otherwise, if any of that business's postcards reached `'mailed'`/`'delivered'` → blue; otherwise the business is excluded (nothing's gone out far enough to plot yet). - **`PostcardMapCard.tsx`** (`'use client'`) — receives `pins` as a server-computed prop (`AnalyticsDashboardViewModel.mapPins`); the industry filter and map camera are local client state, independent of `FilterBar.tsx`'s page-level GET-form filters (which would fight with map zoom/pan on every reload). A Google Maps JavaScript API key is different in kind: it's designed to run in the browser, and its security comes from Google Cloud Console's HTTP-referrer restriction, not secrecy. It must be a **separate** Google Cloud API key from the Places API server key (`GOOGLE_PLACES_SECRET_NAME`) — that one is explicitly restricted to Places API (New) only (see `deployment.md`'s Stage 12 guidance) and must never be widened or reused. - **CSP**: `next.config.ts`'s Content-Security-Policy (Stage 25) was extended to allow `maps.googleapis.com` (script), `fonts.googleapis.com`/`fonts.gstatic.com` (the Maps JS UI chrome's own stylesheet/fonts), and `*.googleapis.com`/`*.gstatic.com` (map tile imagery, XHR) — the first third-party script/style/connect sources this app's CSP has ever allowed.

### Website Visitors (Vercel Web Analytics)

A card at the bottom of `/admin/analytics` showing two lines — homepage (`/`) and self-service build-funnel landing page (`/build`, never the deeper `/build/[buildId]` wizard steps) visitor counts over time — with its own independent date-range control (week/month/3month/6month/year/custom), separate from `FilterBar`'s page-wide filters (same "own local filter" precedent `PostcardMapCard` already set).

Backed entirely by **Vercel's own Web Analytics REST API** (`GET /v1/query/web-analytics/visits/aggregate`), not a custom-built pageview pipeline — no new AWS infra (no DynamoDB table, no ingestion endpoint, no bot filtering to build). Deliberately scoped to exactly these two pages, not the whole `webpresa.com` domain: `/b/[slug]` (customer-generated business sites) can get real postcard-campaign-driven traffic that would otherwise dominate both the number and the Vercel team's shared Web Analytics event quota/cost pool (events are billed/quota'd per team, across every project).

- **Collection**: `app/components/TrackedPageAnalytics.tsx` (`'use client'`), mounted once in the root layout (`app/layout.tsx`). Checks `usePathname()` and renders `@vercel/analytics/next`'s `<Analytics />` only when the path is exactly `/` or `/build` — every other route renders `null`, so nothing else counts against the quota. Deliberately not a route-group split (an earlier draft of this stage moved `page.tsx` into a new `app/(marketing)/` group to scope the script structurally instead — reverted in favor of this zero-file-move approach after review, since a runtime path check achieves the identical scoping without touching existing file locations this far into the app).

## Marketing — SES Drip Campaign

**Implemented and deployed to both dev and prod (2026-08-21).** `/admin/marketing` — a 3-email SES drip campaign automatically triggered by Lob's `postcard.delivered` webhook event, plus the admin dashboard to monitor and operate it. Listed in `AdminSidebar.tsx`'s `NAV_ITEMS` between Analytics and Operations. The campaign itself defaults to `'disabled'` in every environment, including prod — deployment alone never causes a real send.

### Trigger and scheduling

The existing Lob webhook (`app/api/webhooks/lob/route.ts`) calls `startMarketingOutreach()` (`lib/marketing/campaign-start.ts`) only when a newly-recorded event produces a `deliveredAt` — never on postcard creation or send. Enrollment is idempotent (the `MarketingOutreach` composite key's conditional write) and re-checks eligibility once at enrollment time, so a business already claimed/converted between mailing and delivery is never enrolled.

Only the *next* step is ever scheduled — `MarketingOutreach.nextActionSequence`/`nextActionAt` — never all 3 upfront. `computeNextActionAt()` (`lib/marketing/schedule.ts`) always anchors on the original `deliveredAt`, so a late-sent step never drifts the following ones. A new Vercel Cron (`app/api/internal/marketing/send-due-emails`, `0 13 * * *`, `vercel.json`) runs once daily — this app's second use of Vercel Cron, and deliberately not EventBridge Scheduler (no such precedent exists anywhere in `infra/`) — queries the sparse `campaign-next-action-index` GSI for due steps, and calls `attemptSendForOutreach()` (`lib/marketing/send.ts`) per item inside its own try/catch, so one item's failure never aborts the sweep.

### Eligibility (send-time, never assumed)

`checkMarketingEligibility()` (`lib/marketing/eligibility.ts`) is the single function called fresh immediately before every send — the Lob-enrollment hook, the cron, and the manual "send now" admin action all call it, never trusting a prior check. In order: campaign enabled (global kill switch, defaults `'disabled'` in every environment) → outreach still `'active'` → business not `'claimed'`/`'customer'` (`'cancelled'` is deliberately not a stop condition) → target email not in `MarketingSuppression` (unifies unsubscribe/hard-bounce/complaint/admin-suppression) → postcard not engaged (reads `CampaignRecipient.totalScans` directly, Stage 21's existing model, no duplicated flag).

### SES sending and events

`lib/ses/send-marketing-email.ts` — a sibling to Stage 20's `sendLeadNotificationEmail`, using a distinct `MARKETING_SES_FROM_EMAIL` identity (different sending purpose/reputation) and tagging sends with the new `SES_CONFIGURATION_SET_NAME` when set. New CDK stack `infra/lib/stacks/ses-stack.ts` (`WebpresaSesStack`) provisions the Configuration Set, an SNS topic, and an HTTPS subscription straight into `app/api/webhooks/ses/route.ts` (CDK-managed — unlike Lob, no manual dashboard registration step). Matches `send`/`delivery`/`bounce`/`complaint`/`reject` events only — deliberately excludes `open` (unreliable, de-emphasized per product requirements) and `click` (this feature does its own attribution, below).

The webhook (`lib/ses/verify-sns-signature.ts` — the real AWS signature algorithm, no dependency added; SSRF-guarded by validating `SigningCertURL`'s hostname before ever fetching it) mirrors the Lob/Stripe webhook shape: verify → durable write first (`MarketingSesEvent`, conditional on the SNS envelope's own `MessageId`) → conditional rollup only when newly recorded. `Delivery` updates `MarketingMessage`; a hard (`Permanent`) `Bounce` or any `Complaint` writes a `MarketingSuppression` and ends the outreach; soft bounces record only; `Reject` is diagnostic-only.

### Click tracking

`app/e/[token]/route.ts` — a self-contained encrypted JWE (`lib/marketing/click-token.ts`, `jose`, `dir`/`A256GCM`, keyed by the new `marketing-click-token` secret), not a database-backed lookup token, and deliberately separate from `/r/[campaignCode]` (Stage 21's postcard-QR redirect, a different token scheme entirely). An invalid/tampered token is a 404 — unlike the QR redirect, this token is never human-typed or guessable, so there's no enumeration concern to hide behind a generic fallback. `renderTemplate()` wraps `{{previewUrl}}` through this redirect only in the HTML body (the text body uses the raw URL — click tracking only matters for HTML link rendering).

### Unsubscribe

`app/unsubscribe/[token]/route.ts` — public, no auth. `MarketingOutreach.unsubscribeToken` is generated once at enrollment and stored **plaintext** (not hashed like `lib/claim/token.ts`'s claim tokens) — a deliberate deviation, since it must be re-embedded verbatim across 3 emails sent days apart and only ever grants "stop emailing this business," never account takeover. The route resolves the token via `unsubscribe-token-index`, writes a `MarketingSuppression`, ends the outreach if not already terminal, and redirects to a static confirmation page — idempotent, and an unknown token never distinguishes "invalid" from "already used."

### Email templates

Each of the 3 steps is a single plain-text `body` (not separate HTML/text fields) — kept intentionally simple to edit. `renderTemplate()` (`lib/marketing/render-template.ts`) derives both outputs at send time: the text body via plain substitution, the HTML body by HTML-escaping the plain text being converted to markup (a literal `<` in an admin's prose must not be interpreted as a tag) and rendering `{{previewUrl}}`/`{{unsubscribeUrl}}` as real anchor tags. Only `{{businessName}}`, `{{previewUrl}}`, `{{unsubscribeUrl}}` are supported; `validateTemplateVariables()` rejects anything else at save time (Zod `.refine()`) and defensively leaves unrecognized tokens as literal text at render time rather than throwing. Templates resolve at send time (an admin edit takes effect on the next send), but every actual send snapshots its rendered subject/HTML/text onto the `MarketingMessage` row — the durable "what was sent" audit trail. "Send Test Email" calls the identical `renderTemplate()`/`sendMarketingCampaignEmail()` path as a real send (true WYSIWYG parity) but never touches `MarketingOutreach`/`MarketingMessage`, and is still gated by the non-prod recipient allowlist.

### Dev/prod safety

`MarketingCampaign.status` defaults `'disabled'` in every environment. `MARKETING_TEST_RECIPIENT_ALLOWLIST` (`lib/marketing/test-recipient-allowlist.ts`) gates every send outside `production` — both the real send path and "Send Test Email" — to a comma-separated set of exact addresses/`@domain` suffixes; outside production with nothing allowlisted, no marketing email can be sent to anyone.

### `/admin/marketing` UI

`page.tsx` (server component, `force-dynamic` — unlike Analytics' cached view, staleness during active monitoring/manual controls is undesirable) reads `getMarketingDashboardData()` (`lib/marketing/dashboard.ts`, bounded direct reads — `listOutreachForCampaign` via GSI, `listAllMarketingMessages`/`listAllBusinesses` via capped `Scan`, the same "GSI for point lookups, Scan for admin/analytics aggregation" split Analytics/Operations already established). KPI grid deliberately has no open-rate tile. `OutreachTable.tsx` mirrors `BusinessTable.tsx`'s split (server-side status filter via `FilterBar`, client-side instant name/email/business-ID/postcard-ID search over loaded rows); row detail is an **expandable row**, not a drawer, matching this repo's `CollapsibleCard` precedent over its one drawer-like component (a picker modal, not a detail view). `templates/` is its own sub-route with 3 `TemplateEditorCard`s (subject/body, sample-data preview, Save/Reset-with-confirm/Send-Test-Email). All admin mutations are Server Actions with Zod, matching every other admin surface in this app — no new REST routes for admin operations.

3. Captures a screenshot, HTML snapshot, and Lighthouse report
4. Stores artifacts in S3 (keys written to `ScanEvent.storageKeys`)
5. Writes scores to `ScanEvent.scores` and updates `Business.scores`

### Preview generator

A background job that:
1. Reads a `Business` and its `ScanEvent` data
2. Calls an LLM to generate structured `PreviewContent` (validated by `PreviewContentSchema` before storage)
3. Creates a `SitePreview` record via `createSitePreview({ previousVersion })`
4. Renders the preview site and makes it accessible at a preview URL

### Postcard service

A service that:
1. Creates a `Postcard` record via `createPostcard()`
2. Submits the postcard to a mailing provider (Lob, Stannp, or PostGrid)
3. Writes the `providerPostcardId` back to the record
4. Polls or webhooks provider status to update `mailedAt` and `deliveredAt`

Supported providers are defined in `POSTCARD_PROVIDERS` in `domain/models/postcard.ts`.

### Billing

Stripe integration. Stripe Customer ID and Subscription ID are stored on the `Business` record (`stripeCustomerId`, `stripeSubscriptionId`). No payment logic exists yet.
